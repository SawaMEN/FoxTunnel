# Свойства защиты и границы FoxTunnel

**Русский** · [English](SECURITY.en.md) · [Каталог](../README.md)

> **Назначение:** Реальная модель угроз, TLS-проверки, ограничения и незащищённые сценарии.

Это проверка конкретных механизмов прототипа, не внешний аудит и не заявление
«не хуже любого VPN». Защита канала, обнаруживаемость и полнота VPN — разные
свойства. Основа — стандартный TLS 1.3; собственный шифр не разрабатывается.

## Что находится в ссылке

| Поле | Значение |
| --- | --- |
| `username` | Идентификатор доступа; не ключ шифрования |
| `password` | Секрет авторизации; setup создаёт 32 случайных байта через crypto/rand |
| `sni` | Проверяемое DNS-имя сертификата; по умолчанию имя из URL |
| `pin_sha256` | Необязательный дополнительный SHA-256 SPKI pin вида sha256/base64; setup вычисляет его из сертификата |
| `encryption` | Только tls13; AES-GCM/ChaCha20-Poly1305 выбираются безопасным согласованием TLS |
| `tls` | Реализация go/nss; не название шифра |
| `bond`, `discover` | Объединение путей и получение состава с одной главной ноды |

Закрытый ключ TLS, эфемерные ключи сеанса и администраторские параметры в ссылку
не включаются. SPKI pin — отпечаток публичного ключа, а не закрытый ключ.
Для TLS клиенту не нужен серверный закрытый ключ, подобный полю private-key
конфигурации WireGuard. Наличие UUID, SNI или слова «шифрование» в URL само по
себе не доказывает защиту протокола.

Ссылка содержит секрет доступа. Base64url не даёт шифрования/подписи; получать
её нужно из доверенного источника. Настройки не разрешают отключить проверку
TLS, подставить локальные файловые пути или произвольные команды. Локальный
CA задаётся отдельно на своей машине. Старые ссылки без новых полей используют
TLS 1.3 и имя URL; старые клиенты отклоняют неизвестные новые поля.

## Проверяемые гарантии реализации

| Свойство | Текущая реализация и проверка |
| --- | --- |
| Секретность/целостность в сети | TLS 1.3 на каждом переходе; сертификат и h2 до HTTP-авторизации |
| Защита прошлых сеансов | Эфемерный обмен ключами TLS 1.3 по умолчанию; пароль доступа не является ключом шифрования записей |
| Аутентификация сервера | Системные/явно добавленные CA, имя сертификата, при настройке — дополнительный SPKI pin |
| SNI | Строгое DNS-имя без схемы, порта и wildcard; у каждого входа собственная политика |
| Изоляция идентичности | Пулы соединений и Go session cache разделены по origin/SNI/pin; изменение pin не пользуется старым ticket cache |
| NSS | x509-цепочка/имя проверяются до VerifyConnection; pin применяется и в NSS, непроверенный режим запрещён |
| Авторизация | Basic внутри проверенного TLS; сравниваются хеши фиксированной длины; setup создаёт сильный случайный пароль |
| Повторы | Защита записей TLS и отдельные sequence/ACK/dedup/срок открытия bond; 0-RTT данных не включён |
| Дорогая работа | 256 авторизованных обработчиков по умолчанию до DNS/dial; ограниченные окна и сессии |
| Неавторизованные сокеты | Серверный лимит 512 принятых сокетов, включая незавершённый TLS, плюс тайм-аут заголовков |
| Локальный вход | Loopback SOCKS5 по умолчанию; до 256 сокетов, включая незавершённый SOCKS |
| Публичный сайт | Без листинга/dotfiles, выходов через symlink за корень и известных конфигураций/ключей; проверка пересечения с закрытыми путями |
| Файлы подготовки | Новый каталог 0700, файлы 0600, отказ перезаписи, секреты не печатаются |

Pin не заменяет CA, имя, срок сертификата или h2. Ошибка pin/сертификата не
запускает переход на менее строгий режим. Для IP-адреса и DNS-сертификата можно
задать соответствующий SNI; произвольное чужое имя не пройдёт проверку.
SNI обычно виден наблюдателю; ECH не реализован. HTTP authority GET/POST
соответствует явному SNI, а CONNECT сохраняет адрес назначения.

Прямой CONNECT и bond используют одни проверки. Главная нода из доверенной
ссылки может делегировать доступ входам из своего авторизованного состава.
TLS завершается на каждом узле: входы доверенные и видят туннелируемые данные.
HTTPS приложения остаётся сквозным, если приложение его использует.
Это не анонимная сеть и не защита от скомпрометированной доверенной ноды.

## Что остаётся слабее зрелого VPN-продукта

- SOCKS5 TCP дополнен **отключённым по умолчанию** экспериментальным UDP ASSOCIATE (по одной датаграмме через HTTPS POST); пока нет TUN, потокового UDP и системного kill switch. Подробные лимиты и безопасность: [UDP](../architecture/UDP.md).
- Реле UDP использует ту же аутентификацию и фильтрацию IP; защищённый контрольный TCP-сокет ограничивает срок жизни локального UDP-порта. Нет защиты от потерь при переключении сети. Полное отсутствие утечек DNS не заявляется.
- Пока нет универсального VPN, системной маршрутизации, DNS-контроля и kill switch
  и гарантии перехвата всего DNS/трафика ОС. Приложение может обращаться в сеть
  напрямую, если его не настроили на прокси.
- Нет независимого аудита собственного кода/форматов и полевого доказательства
  устойчивости к российским ТСПУ. NSS + Go H2 не равны Firefox.
- Нет привязки прикладной авторизации к TLS exporter, как в TUIC v5. Секрет
  является bearer credential внутри TLS; его утечка требует смены учётных данных.
- Лимиты ресурсов не заменяют защиту от распределённого DoS или сетевого
  переполнения полосы. Глобальной телеметрии кластера и индивидуальных ключей/
  отзыва пользователей пока нет: настройка использует одну пару на сервере.
- Главная нода — общая точка отказа и ограничения полосы. Потеря её сокетов
  не скрывается повторным открытием приложения на другом выходе.
- Выдача/продление сертификатов остаётся задачей оператора. Версионные Linux
  NSS-архивы включают закреплённые библиотеки Mozilla; для их обновления нужен
  новый выпуск FoxTunnel. Сборки разработчика/SDK используют своё окружение
  NSS/NSPR. Native-библиотеки не проверяются Go-сканером.

Поэтому сравнивать нужно конкретные свойства: TLS-защиту и ошибки проверки,
авторизацию, повторы, пределы памяти, UDP/маршрутизацию, DNS/kill switch,
стабильность и результаты независимых испытаний. Таблица не является рейтингом.

## Проверки этого изменения

Go/NSS end-to-end и race-тесты: правильный SNI/pin, неверные имя/ключ/CA,
отсутствие HTTP до проверки, изоляция настроек fallback/входов, потеря ACK и
входной ноды, полузакрытие. Проверены setup → серверный JSON → запуск без
credential environment, присоединение/повторное добавление ноды, права файлов,
отказ перезаписи и ошибочные сертификаты. Есть фаззинг ссылок/состава, тест
незавершённого SOCKS под лимитом и запрета выдачи закрытых файлов/symlink escape.

Методика известных уязвимостей: govulncheck v1.9.0, Go 1.26.9, исходники,
уровень символов, база vuln.go.dev (наблюдаемое обновление 2026-10-08).
Оба сканирования (обычное и с тегом nss) завершились с кодом 0 без findings.
Проверка добавлена в обе задачи CI. Это не доказывает отсутствие неизвестных
ошибок или проблем native NSS. Регрессионный тест общих ticket keys проверен
также на намеренно ослабленной копии: без изоляции session cache он обнаруживает
обход pin, с текущей реализацией проходит.

См. [подготовку](../guides/SETUP.md), [Amnezia/TUIC](../archive/reviews/AMNEZIA-TUIC-REVIEW.md)
и [формат ссылок](../guides/CONNECTION-LINKS.md).
Криптографическая основа: [TLS 1.3, RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html).

## Новые встроенные транспорты

H2 POST, WSS и H3 POST/QUIC сохраняют проверки CA/SNI/pin и авторизацию.
WSS также проверяет секрет до Upgrade; внутренние H2-запросы авторизуются отдельно.
Сжатие WebSocket и QUIC 0-RTT выключены. Размеры сообщений, заголовки, потоки,
окна и входные соединения ограничены. Эти меры не заменяют внешний аудит.
Свойства и пределы — в [описании транспортов](../architecture/NATIVE-TRANSPORTS.md).

После добавления зависимостей `govulncheck` не выявил достижимых уязвимостей
или уязвимостей импортируемых пакетов. На уровне модуля он отмечает
GO-2026-5932 для неиспользуемого `golang.org/x/crypto/openpgp`; этот пакет
не импортируется. Нативные библиотеки NSS требуют отдельного сопровождения.

# Пользователи, отзыв доступа и квоты

**Русский** · [English](ACCESS.en.md) · [Каталог](../README.md)

> **Назначение:** Пользователи, отзыв, ротация, лимиты запросов и долговременные квоты.

Пятый этап добавляет управляемый доступ на Linux. Это локальная политика сервера,
без сетевого admin API. Старый режим одной пары `FOXTUNNEL_USER` /
`FOXTUNNEL_PASSWORD` сохранён. Управляемый режим выбирается явно и не допускает
одновременных legacy credentials. Клиентский wire-формат и ссылки не меняются:
каждый пользователь получает собственную пару username/password.

## Начальная настройка

Создайте отдельный закрытый каталог, вне `--web-root`. Пароли — случайные секреты,
а не человеческие слова; минимум 24 байта, максимум 1024. Например, от root:

```sh
install -d -m 700 /etc/foxtunnel/access
umask 077
python3 - <<'PY'
import json, secrets
users = [{"id": name, "username": name, "password": secrets.token_urlsafe(32),
          "max_tunnels": 32, "max_requests": 128,
          "requests_per_second": 100, "burst": 200,
          "quota_bytes": 10737418240}
         for name in ("alice", "bob")]
with open('/etc/foxtunnel/access/users.json', 'x') as f:
    json.dump({"v": 1, "users": users}, f, indent=2)
PY
foxtunnel access --users-file /etc/foxtunnel/access/users.json
```

Последняя команда проверяет конфигурацию и выводит только ID, disabled и квоты.
Она не выводит логины или пароли. Передайте каждому клиенту только его секрет
через существующее защищённое окружение/личный файл ссылки; весь users.json
клиентам не нужен. Для миграции короткого legacy-пароля сначала выдайте новый.

Запуск с TLS-сертификатом и обычными сетевыми ограничениями:

```sh
unset FOXTUNNEL_USER FOXTUNNEL_PASSWORD
foxtunnel server --listen :443 --cert /etc/foxtunnel/cert.pem \
  --key /etc/foxtunnel/key.pem \
  --users-file /etc/foxtunnel/access/users.json \
  --users-state /etc/foxtunnel/access/usage.json
```

В `server.json` версии 1 доступны `users_file` и `users_state`. При их использовании
уберите `username`/`password` или задайте пустые строки. Оба пути обязательны;
остальные настройки/проверки сервера действуют как прежде. Файл пользователей —
обычный файл с правами 0600 (0400 также подходит); симлинки и доступ группы/других
отвергаются. Каталог журнала — 0700, сам журнал/lock — 0600. Users и state не могут
быть одним файлом, в том числе через hardlink. Первая инициализация создаёт журнал.

## Лимиты и единицы

| Поле | По умолчанию | Что ограничивает |
|---|---:|---|
| `max_tunnels` | 32 | Выходные TCP-сокеты одного пользователя, включая DNS/dial |
| `max_requests` | 128 | Одновременно обрабатываемые приватные HTTP-запросы, включая carriers и bond RPC/lanes |
| `requests_per_second` / `burst` | 100 / 200 | Token bucket пользователя: запросы, а не байты/с |
| `quota_bytes` | 0 | Сумма upload + download на выходном TCP-сокете; 0 — без ограничения |
| `attempts_per_second` / `attempt_burst` в корне | 200 / 400 | Общий token bucket приватных попыток, включая неверную авторизацию |
| `max_requests` в корне | 1024 | Общая параллельность управляемых приватных запросов |

Пример выше задаёт каждому **накопительную** квоту 10 ГиБ, без календарного сброса.
Учитываются данные у назначения, включая прочитанные, но ещё не доставленные
клиенту байты; не TLS/HTTP overhead и не padding. Повторы bond учитываются только
при единственной доставке/чтении у общего выхода. Параллельные операции резервируют
бюджет до I/O; остаток возвращается после короткого I/O. На самой границе квоты
поток может быть оборван до доставки последней порции. Это верхний предел, не
гарантия доставки ровно указанного числа байтов.

Частотные и конкурентные ограничения возвращают 429 известному пользователю.
Неверные/отозванные credentials и исчерпанный общий бюджет попыток идут в тот же
cover/404, без выдачи состояния аккаунта. Уже открытый поток закрывается при
исчерпании квоты. Лимиты `--max-connections`, `--max-tunnels`, окна H2/H3, XHTTP и
bond продолжают действовать. Нет растущей таблицы по IP/неверным username: до
1024 настроенных пользователей и 4096 исторических ID в учёте. RPS/квоты не
являются ограничением полосы и не заменяют внешний лимит входящих соединений.

## Отзыв, ротация и перезагрузка

Изменяйте users.json через временный файл 0600 и atomic rename в том же каталоге,
затем проверьте `foxtunnel access --users-file ...` и отправьте серверу:

```sh
kill -HUP "$FOXTUNNEL_PID"
```

- Отзыв: `disabled: true` либо удаление записи. Меняются только сессии этого ID.
- Ротация: новый случайный `password` в той же записи, с прежним `id`.
  Старый пароль перестаёт работать, активные соединения этого пользователя
  закрываются; новый секрет нужно отдельно передать его клиентам.
- Изменение индивидуальных лимитов/username также закрывает прежнюю генерацию
  соединений. Неизменённые пользователи сохраняют соединения и rate buckets.
- Неверный, частичный, неизвестный/дублированный JSON или недопустимые лимиты
  отклоняются целиком; текущая политика остаётся. `users: []` отзывает всех;
  пропущенный/null `users` в файле — ошибка.

Квота и счётчики сохраняются при ротации, удалении и повторном добавлении того же
ID. Не меняйте ID ради обычной ротации и не удаляйте журнал. ID: 1–64 символа
`a-z`, `0-9`, `_`, `-`, уникален; username тоже уникален. Пароли между узлами не
синхронизируются автоматически. Для отзыва в кластере обновите общий выход и все
входы; отзыв только одного входа не запрещает доступ через другой.

XHTTP пары и bond токены привязаны к ID и генерации. Другой пользователь не может
подключиться к чужому token/UUID. Внутри WSS/XHTTP нельзя сменить пользователя
новым заголовком Basic. Отзыв закрывает и тихие сокеты, carriers и bond-сессии;
обычное завершение отдельного HTTP retry не отменяет общий bond-выход.

## Журнал и диагностика

Перед выдачей байтов резерв записывается через fsync файла, atomic rename и fsync
каталога. Блокировка ОС разрешает только одного владельца журнала; после аварии
процесса lock освобождается без удаления lock-файла. При ошибке записи доступ
закрывается: непосчитанные данные не отправляются. Повреждённый существующий
журнал блокирует запуск. Нужен локальный файловый слой с рабочими fsync/flock.

Чтобы не делать fsync на каждый пакет, резерв пополняется порциями до 1 МиБ.
После перезапуска неиспользованный резерв считается потраченным. Возможна
консервативная потеря доступной квоты: до 1 МиБ плюс незавершённые резервы I/O
(до 32 КиБ на чтение и на запись каждого активного сокета). Уменьшение квоты не
отменяет уже выданные резервы. Журнал содержит накопительные charged bytes;
точный `bytes_this_process` в памяти начинается с нуля при запуске. Это не
биллинг с помесячными периодами, распределённая БД или защита от отката файла
самим администратором. Не восстанавливайте старый журнал как способ ротации.

```sh
# Офлайн: только сохранённые консервативные списания; требует существующего state.
foxtunnel access --users-file /etc/foxtunnel/access/users.json \
  --users-state /etc/foxtunnel/access/usage.json
# Живые счётчики в журнал процесса (ID, bytes, active, limits; без credentials):
kill -USR1 "$FOXTUNNEL_PID"
```

У CLI нет автоматического журналирования запросов, адресов назначения, заголовков
или ссылок. Ошибки access parser/reload не содержат фрагментов входа. Логи чужого
reverse proxy/хоста настраиваются отдельно; не включайте запись Authorization.

## Bond и SDK

Квоты уникальных данных задавайте на **общем выходе** с `--bond-hub`. На relay
с `--bond-upstream` управляйте авторизацией и HTTP-лимитами; `quota_bytes` должен
быть 0 — ненулевая relay-квота отвергается, чтобы не создавать ложное ограничение.
Управляемый relay не открывает обычные CONNECT/POST-выходы: через carriers
допускается только bond к общему выходу, чтобы клиент не обошёл его квоту.
Relay передаёт исходные credentials пользователя, а не заменяет их общим логином.
На выходе и входах нужны соответствующие учётные записи. Общая квота находится
на одном выходе; независимые выходы не объединяют бюджеты автоматически.

SDK: `NewAccessController(AccessPolicy{Version:1, Users:[]AccessUser{...}}, stateFile)`,
затем `NewServer(ServerConfig{Access: controller, ...})` без `Credentials`.
Хост вызывает `controller.Replace(policy)`, `Snapshot()` и `Close()`.
Непустой stateFile включает Linux-журнал и эксклюзивную блокировку; пустой путь
**явно** выбирает учёт в памяти, который сбрасывается при перезапуске. TLS/CA/pin
и внешние ограничения слушателя остаются обязанностью хоста.

Тесты: независимые пользователи на семи транспортах и NSS, SOCKS/SDK, ротация,
закрытие тихого dial/потока, запрет смены владельца, bond RPC/lane hijack и
дедупликация квоты, конкурентное исчерпание, restart/lock/ошибка state, SIGHUP и
редактирование диагностики. Внешний аудит и длительные/platform испытания остаются
следующими этапами.

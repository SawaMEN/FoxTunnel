# Самостоятельные версионные бинарники

**Русский** | [English: полный контракт и команды](DISTRIBUTION.en.md)

FoxTunnel поставляется как отдельный исполняемый файл. Любая панель, включая
3x-ui, или клиент на другом языке сможет скачивать конкретную версию и управлять
её процессом. Код панели, её БД, Xray или закрытый сервис не требуются. Go SDK —
дополнительный способ встраивания.

Pipeline GitHub Releases поддерживает два явных запуска: существующий тег
`vMAJOR.MINOR.PATCH[-pre]` или изменение `.github/release-request.json` через
проверенный PR в main. Во втором случае CI сначала собирает и проверяет все
артефакты, затем создаёт тег на точном проверенном commit и публикует prerelease.
Обычные main-коммиты и PR собираются с `v0.0.0-ci` без публикации. Ошибка/отсутствие
одной платформы блокирует выпуск; существующие теги/релизы не перезаписываются.

| ОС | Архитектуры | Варианты |
|---|---|---|
| Linux | amd64, arm64 | go, nss |

**Четыре архива на выпуск:** Linux amd64/arm64 × Go/NSS. Сборки для macOS, Windows и Linux armv7 не публикуются.

Формат имени: `foxtunnel_VERSION_linux_ARCH_FLAVOR.tar.gz` (без начального `v`).
Каждый архив содержит бинарник `foxtunnel`, `build.json`, MIT-лицензию, лицензии модулей и сведения о третьих сторонах. NSS-вариант дополнительно включает неизменённые библиотеки NSS/NSPR/SQLite из Firefox и `mozilla-runtime.json` с происхождением и SHA-256 библиотек.

Go-вариант собирается с CGO=0. NSS требует совместимые glibc и libgcc-s1; база CI — Ubuntu 24.04. Библиотеки NSS расположены в `lib/` рядом с бинарником и не должны удаляться. Даже NSS-вариант использует TLS backend `go` по умолчанию, `nss` выбирается явно. Ни один вариант не воспроизводит полный сетевой стек Firefox.

`manifest.json` и `SHA256SUMS` **не создаются и не публикуются**. При сборке локальные `*.metadata.json` используются для проверки CI, но не входят в релиз. CI проверяет все четыре архива, однородность версии/commit, встроенные метаданные и состав файлов перед публикацией. Из этого не следует наличие внешней криптографической подписи релизного архива.

Алгоритм для панели:

1. Выбрать точный проверенный тег и соответствующий полный source commit, не использовать `latest`.
2. Определить поддерживаемую платформу `linux/amd64` или `linux/arm64` и вариант `go`/`nss`; скачать архив этого тега.
3. Выполнить проверку `scripts/release.py verify` (пример ниже), затем распаковать в отдельный каталог версии, отклоняя небезопасные пути.
4. После распаковки запустить `foxtunnel version --json`, сверить schema, version, commit, Linux/CPU, draft, backend и `dirty: false`.
5. Запускать `client --link-file PRIVATE_FILE --listen 127.0.0.1:1080` или `server --config PRIVATE_SERVER_JSON`; передавать секреты приватными файлами и окружением, не через shell.
6. При обновлении останавливать предыдущий процесс, оставляя каталог старой версии для отката; активные TCP-потоки не мигрируют.

x86_64 соответствует amd64, aarch64 — arm64. Linux armv7, Windows и macOS не входят в релизную матрицу. Все команды CLI, включая setup/share/cluster-add, остаются в бинарнике.

JSON версии содержит также сведения Go, ARM variant, build flavor, TLS backends,
признак experimental и идентификатор `foxtunnel-draft-0`. Дополнительные поля
допускаются, неизвестная schema/draft — нет. Совместимость чернового протокола/API
пока не обещается автоматически: интегратор закрепляет проверенную версию.
Отдельного внешнего списка контрольных сумм и контракта подписей нет: получайте архивы только из доверенного источника.

Команды локальной сборки и детали pipeline — в английской версии. `--allow-dirty`
допустим только для локального preview: проверка релиза такую сборку не принимает.

[SDK](SDK.md) · [Спецификация обмена](WIRE-DRAFT-0.md) · [MIT](../../LICENSE)

NSS runtime закреплён в `scripts/mozilla-runtime.lock.json`. SHA-256 проверяется
до извлечения; разрешены только ожидаемые обычные файлы. ELF RPATH ищет библиотеки
относительно бинарника, сборка проверяет их архитектуру, зависимости и версию NSS.
CI выполняет TLS/XHTTP-тесты на amd64/arm64 и в Ubuntu-контейнере без системных
NSS/NSPR. Обновление Mozilla требует новых проверенных хешей и новой версии
FoxTunnel; прежние релизные файлы не заменяются. Обычная сборка Go SDK с тегом
`nss` по-прежнему использует окружение разработчика. Совпадение версии NSS ещё
не означает совпадение TLS/HTTP-отпечатков Firefox или защиту от классификации ТСПУ.

## Независимая проверка скачанного комплекта

Из проверенного checkout с Python 3.11+ скачайте нужный архив в `downloaded/`:

```sh
python3 scripts/release.py verify --input downloaded \
  --version "$RELEASE_TAG" --commit "$RELEASE_COMMIT" --target linux/arm64/nss
```

Без `--target` проверяются все четыре Linux-архива. Для проверки одной сборки остальные три не нужны. Проверка читает `build.json` прямо из архива, сверяет ожидаемые версию и commit, проверяет файлы, права доступа, опасные пути, повторяющиеся имена, NSS provenance и хеши библиотек, не распаковывая и не запуская двоичный код. `*.metadata.json` получателю не нужен.

**Ограничение:** без независимо доверенного SHA-256/подписи нельзя доказать подлинность скачанного архива только по его собственному `build.json`. Ожидаемый commit и источник загрузки должны быть доверенными; проверка структуры не заменяет подпись или attestations.

CI использует Go 1.26.9 и требует успешных Go vet/race, внешнего SDK, Python-тестов, обоих нативных NSS jobs и проверки четырёх архивов.

## Выпуск через проверяемое изменение версии

В `.github/release-request.json` указывают только `schema: 1` и новый `version`.
В `docs/releases/VERSION.md` готовят примечания. PR проверяет запрос и собирает
CI-комплект без публикации. После слияния в main workflow сравнивает файл запроса
между before/source commit; только его изменение разрешает выпуск. Полная история
нужна для этой проверки; неизвестный before commit не разрешает публикацию.

Перед публикацией все четыре архива заново строятся с запрошенной версией и
одним source commit, проходят index/offline verify и NSS-проверки. Job публикации
создаёт тег именно на этом commit. Неизменённый запрос не выпускается повторно
при обычном обновлении кода. Существующий тег/релиз приводит к отказу, а не замене.
Для следующего выпуска нужен новый version. Обычный запуск по заранее созданному
тегу также сохранён; все выпуски этого workflow остаются prerelease.

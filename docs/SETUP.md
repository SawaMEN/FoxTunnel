# Простая подготовка главной и входных нод

**Русский** | [English](SETUP.en.md)

`setup` автоматически создаёт случайный 256-битный секрет, серверную
конфигурацию, описание ноды и ссылку `vetroff://` с SNI, TLS 1.3 и отпечатком
публичного ключа. Секреты не печатаются. Каталог создаётся с правами 0700,
файлы — 0600; существующий каталог не перезаписывается.

Нужны готовые действительные сертификат и ключ для вашего домена. Их получение,
обновление, DNS, установка программы и firewall этим CLI не автоматизируются.
`setup` проверяет соответствие ключа, цепочку, имя и срок сертификата
(должно оставаться хотя бы 24 часа). Непроверенный сертификат не принимается.

## Главная нода: две команды

```sh
./foxtunnel setup --server https://main.example \
  --cert /etc/certs/main/fullchain.pem --key /etc/certs/main/key.pem \
  --web-root /srv/public-site --out main-node
./foxtunnel server --config main-node/server.json
```

Переменные с паролем задавать не нужно. Главная нода стартует с собственным
прямым входом; другие ноды добавляются позже. Пользователю передаётся только
`main-node/connection.txt`:

```sh
./foxtunnel client --link-file connection.txt
```

Серверный JSON и приватный ключ остаются у администратора. Ссылка содержит
секрет доступа и передаётся доверенным способом. Кодирование base64url не
шифрует файл. Для экспериментального NSS добавьте `setup --tls-backend nss`: профиль потребует
клиентскую сборку с NSS. Обычный `setup` выбирает Go. Смешивать импортированную
ссылку с флагом `client --tls-backend` нельзя; при присоединении входа сохраняется
клиентский профиль главной ноды.

## Входная нода

На входной ноде используйте её сертификат и файл подключения главной ноды:

```sh
./foxtunnel setup --server https://node-a.example \
  --cert /etc/certs/node-a/fullchain.pem --key /etc/certs/node-a/key.pem \
  --join-link-file main-connection.txt --out node-a
./foxtunnel server --config node-a/server.json
```

Секрет кластера и проверка главной ноды импортируются автоматически. Вход
использует SNI и pin главной ноды из ссылки. Его `connection.txt` сохраняет
пользовательское подключение к главной ноде.

Передайте **публичный** `node-a/node.json` администратору главной ноды и выполните
там:

```sh
./foxtunnel cluster-add --config main-node/server.json --node-file node-a.json
```

Команда проверяет адрес, SNI и pin, добавляет/обновляет ноду и атомарно заменяет
состав на Linux. Перезапуск и перевыпуск ссылок не нужны. Повторное добавление
того же URL обновляет запись. Одновременные команды защищены lock-файлом;
после аварийного завершения оставшийся `.lock` удаляют только убедившись,
что другой `cluster-add` не работает. Команда не подключается к ноде и не
проверяет её фактическую доступность: клиент измеряет путь при использовании.

Всего до восьми входов, включая прямой вход главной ноды и отключённые записи.
Начальный вес каждой ноды — 1; веса/отключение редактируются в `cluster.json`.
Автоматической оценки мощности всех серверов пока нет. Обновления применяются
к новым сессиям; старые нужно завершить перед остановкой удаляемой ноды.

## SNI, IP-адрес и частный CA

Если подключение идёт по IP, укажите имя, присутствующее в сертификате:

```sh
./foxtunnel setup --server https://203.0.113.10 --sni main.example \
  --cert fullchain.pem --key key.pem --out main-node
```

Нельзя подставить произвольный чужой SNI: цепочка и имя проверяются. SNI не
является секретом; ECH пока не реализован. Для DNS-адреса имя выбирается из URL.
HTTP authority для GET/POST соответствует заданному SNI; CONNECT сохраняет
адрес назначения. Настройки главной ноды не переносятся автоматически на входы:
каждый получает собственные SNI и pin из своего `node.json`.

Для частного CA при `setup` задайте `--ca-cert ca.pem`, на клиенте — локальный
`--ca-cert ca.pem`. Входу для частного CA главной ноды нужен
`--bond-ca-cert main-ca.pem` при подготовке. Корни доверия и локальные пути CA
в ссылку не внедряются; pin не отменяет проверку CA. Если у нод разные CA,
клиентскому PEM нужны соответствующие доверенные корни.

## Изменение параметров

`server.json` содержит адрес прослушивания, лимиты, пути сертификатов, закрытые
учётные данные и роль. `server --config` не смешивается с флагами настройки
сервера; отредактируйте файл и перезапустите процесс. Язык выбирается `--lang`.
По умолчанию сервер слушает :443, допускает 512 принятых сокетов и 256
авторизованных обработчиков; клиент допускает 256 SOCKS-сокетов, включая
незавершённые подключения. Локальный лимит меняется `client --max-connections`.

Обновление сертификата с прежним публичным ключом сохраняет SPKI pin. При смене
ключа главной ноды нужна новая доверенная ссылка; при смене ключа входа — новый
`node.json` и обновление состава. Автоматического обхода несовпавшего pin нет.
Сертификат сервер загружает при запуске: после обновления нужен перезапуск.

Публичный сайт должен содержать только публичные файлы. Закрытые настройки и
ключ нельзя размещать под `--web-root`; символьные ссылки наружу запрещены.
Общие ограничения — [защита и сравнение](SECURITY.md), [кластер](CLUSTER.md).

## Встроенный транспорт

Добавьте `setup --transport h2-post`, `--transport wss` или
`--transport h3-post`. Выбор сохраняется в ссылке; H3 автоматически включает
UDP-слушатель `:443` в серверном JSON. NSS доступен для H2/WSS, H3 требует Go.
При присоединении входа профиль наследуется от главной ноды.
Подробнее — [встроенные транспорты без Xray](NATIVE-TRANSPORTS.md).

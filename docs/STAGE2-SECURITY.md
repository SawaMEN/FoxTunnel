# Этап 2/8 — безопасность FoxTunnel

Рабочая ветка: up. Эта итерация устраняет различия между legacy
Basic-авторизацией и управляемым access-контроллером, усиливает
разделение публичного cover и приватного протокола, добавляет regression/fuzz.

## Что сделано

1. Единый ограниченный декодер Proxy-Authorization: один заголовок, не больше
   2048 байт, строгий канонический Base64, имя 1..256 печатных ASCII символов
   без двоеточия и секрет 1..1024 байта. Повторы заголовка, включая разное
   написание регистра ключа в SDK, отклоняются. Неверные запросы не возвращают
   значения полей и не записывают секреты в журнал.
2. Одинаковая проверка заголовка в legacy Server.authorized и access.Begin.
   Существующая постоянновременная сверка SHA-256, отзыв учётных данных,
   квоты и лимиты доступа сохраняются.
3. Публичный cover не получает Proxy-Authorization и заголовки
   X-FoxTunnel-*. Исходный запрос не изменяется. Это не превращает публичный
   cover в безопасный reverse proxy произвольных сайтов.
4. Граничные случаи проверяются Go unit-тестами, race detector и
   fuzz-тестом парсера. CI тестирует только изолированный local harness.

## Безопасность и совместимость

- Legacy-учётные данные по-прежнему представляют Basic-авторизацию внутри
  TLS 1.3. Компрометация plaintext-пароля позволяет повторно использовать
  его до ротации; новой anti-replay схемы здесь нет. TLS не гарантирует
  защиту от replay уже украденного прикладного секрета.
- Для реальных пользователей используйте управляемый access с
  индивидуальными сильными секретами (минимум 24 символа для этого режима),
  возможностью отзыва через смену policy и отдельными ограничениями.
- Старые неканонические Base64 значения и заголовки с пробелами/CRLF теперь
  отвергаются. Нормальные клиенты FoxTunnel используют канонический Basic.
  Совместимость нужно дополнительно подтвердить на всех запущенных клиентах.
- Должен использоваться TLS endpoint с проверенным сертификатом. При
  интеграции SDK оператор отвечает за TLS и запрет plaintext HTTP.
- На публичном сервере оставляйте AllowPrivate=false и защищённые
  configuration/state files; приватные target — только в лаборатории.
- Не утверждается защищённость от активного DPI, идентичность Firefox,
  полная формальная верификация криптографии или подтверждение VDS тестов.

## Локальная проверка

~~~sh
go test ./internal/authheader ./internal/access ./internal/tunnel
go test -race ./internal/authheader ./internal/access ./internal/tunnel
go test ./internal/authheader -run '^$' -fuzz '^FuzzParse$' -fuzztime=2000x
go vet ./internal/authheader ./internal/access ./internal/tunnel
~~~

## Оставшаяся работа

1. Протестировать ротацию, отключение устройства и отзыв существующих
   долгоживущих соединений под WAN-нагрузкой.
2. Провести независимый security review (включая backend Go/NSS/Neqo,
   Basic credentials, HTTP2/3, WSS/XHTTP, Bond и UDP/TUN).
3. Решить, нужен ли новый несовместимый auth-режим с короткоживущими
   токенами и anti-replay, только со спецификацией wire-версий.
4. Провести реальные сетевые испытания этапа 1.

CI с чистой сборкой, обязательные Go tests/race/fuzz/vet и положительный
независимый review критических путей аутентификации, шифрования,
авторизации и выхода на destination. Успешный CI — не независимый аудит.

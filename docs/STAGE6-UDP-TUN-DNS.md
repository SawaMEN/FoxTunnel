# Stage 6/8 — UDP, Linux TUN, DNS, IPv6

**Режим:** только локальные испытания и GitHub Actions в ветке `up`;
ни один критерий этапа не требует настоящих VDS или WAN.
**Статус: 5 из 5 (100%) — завершены локальные критерии этапа 6.**
Этапы 1–4 включают fail-closed SOCKS, DNS/killswitch и native
TCP/UDP/DNS IPv4/IPv6 E2E; этап 5 добавил ограниченный реальный
Linux netns soak c контролем RSS, файловых дескрипторов и UDP-сокетов.
Подтверждение: [native TUN CI](https://github.com/SawaMEN/FoxTunnel/actions/runs/39448375868),
[Go Tests](https://github.com/SawaMEN/FoxTunnel/actions/runs/39448376040).

## Что уже существовало

- `internal/nativetun/linux.go`: локальный Linux TUN c userspace
  gVisor IPv4/IPv6, TCP и UDP forwarding через **локальный SOCKS**;
  маршруты ОС и системный DNS модуль сам не меняет.
- `scripts/linux_tun_companion.py`: необязательная обвязка sing-box
  с DNS detour по SOCKS и **отдельным** nftables OUTPUT guard; при
  аварии клиента guard остаётся активен.
- `scripts/test_linux_tun_e2e.py`: управляемые netns, сервер
  FoxTunnel, проверка TCP/UDP/DNS/IPv4/IPv6/kill-switch.
- Существующие workflow `tun-netns.yml`, `native-tun-e2e.yml`
  прежде запускались автоматически только для `main`, поэтому
  безопасность изменений в `up` проверялась неполно.

**Ограничение:** TUN-модуль — forwarding, не полный VPN kill-switch.
Без nft guard, системных маршрутов и DNS policy он не может обещать
отсутствие прямых соединений со стороны других процессов.

## Подэтап 1: отмена SOCKS-рукопожатий и DNS leak guard

Контекст `net.Dialer.DialContext` раньше защищал лишь фазу TCP connect:
медленный SOCKS5 сервер мог принять соединение, но не отвечать на
приветствие или команду. `ReadFull` продолжал ждать до фиксированного
8-секундного timeout, даже если вызывающая сторона уже отменена.

Добавлены:
- `context.AfterFunc(ctx, conn.Close)` в `dialSOCKS` и
  `dialUDPSOCKS` **только на время handshake** (callback снимается
  перед возвратом успешного соединения; долгоживущий UDP control
  channel не закрывается после завершения вызова).
- Нормализация возникающего при отмене `net.ErrClosed` в
  `context.Canceled` / `context.DeadlineExceeded`.
- `TestStage6SOCKSHandshakeCancellation`: четыре комбинации
  TCP CONNECT/UDP ASSOCIATE × stalled greeting/reply, проверка
  немедленного освобождения TCP-сокета на loopback.
- `TestStage6SOCKSHandshakeDeadlineExceeded`: таймаут с IPv6
  SOCKS destination без локального DNS-запроса.
- Дополнительные настоящие **kernel netns** probes: для
  TCP и UDP DNS 53, DNS-over-TLS TCP 853, QUIC/UDP 8443,
  IPv4/IPv6 в режимах разрешённого TCP и UDP carrier.
  Явно разрешён только зафиксированный IP:port FoxTunnel exit.
- В workflow `tun-netns.yml` и `native-tun-e2e.yml`
  включена ветка `up`; Go-часть native TUN тестируется с `-race`.
  Эти привилегированные тесты создают уникальные изолированные netns
  и **не изменяют** хостовый firewall.

## Подэтап 2: повторные Linux native TUN E2E

В `scripts/test_linux_tun_e2e.py` реальный SOCKS→TUN→HTTPS прокси
проверяется трижды для TCP и UDP на IPv4/IPv6. DNS-запросы A и AAAA
на обеих семьях адресов также повторяются трижды; workflow
`native-tun-e2e.yml` выполняет полную лабораторию два раза,

**внутри изолированного netns**.
Проверено: [Native TUN CI](https://github.com/SawaMEN/FoxTunnel/actions/runs/39441292741).

## Подэтап 3: UDP ASSOCIATE и UDP Stream

Поведение `internal/tunnel/udp_client.go` ужесточено:

- Ответ однократного UDP-запроса должен совпадать с исходным
  числовым IP (с нормализацией IPv4-mapped) **и портом**.
  Раньше сравнивался лишь порт. Для DNS-имени ответ содержит
  числовой IP, полученный на доверенном удалённом узле; локальный
  DNS-запрос клиента для проверки не выполняется.
- `udp_stream_client.go` и `udp_multinode_client.go` теперь
  ведут ограниченный **64 запрошенными адресами на выходной узел**
  список разрешённых ответов. Непрошенные ответы с чужого IP/порта
  отбрасываются; выходы не разделяют разрешения между собой.
- Исходная привязка UDP ASSOCIATE к IP TCP control peer и к
  **первому корректному UDP source port** сохранена. Проверены
  попытки с другого локального UDP-порта, `FRAG != 0`,
  некорректный `ATYP`, превышение `MaxDatagram` и короткие
  пакеты. Невалидные пакеты не занимают источник.
- `ReadFrame` отбрасывает нулевую/слишком большую длину,
  укороченные и фрагментированные кадры с освобождением
  `activeTunnels` после закрытия HTTP stream. Ограничения
  (в частности, 8 одновременных one-shot exchanges, 16 потоков
  назначения и 32 элемента очереди stream) сохранены.
- `TestStage6UDPStreamDropsUnsolicitedRepliesOverH2` использует
  настоящий TLS/H2 транспорт. Тестовый узел посылает ложный ответ
  с другим IP на **тот же порт**, затем корректный ответ: приложению
  доставляется только корректный.
- `TestStage6UDPStreamingReplyGuardBoundedAndConcurrent` проверяет
  отсутствие бесконечного роста allowlist и безопасность конкурентных
  чтений/записей под `-race`.

Проверки: `go test -race ./internal/tunnel -run '^(TestStage6UDP|TestUDPAssociate|TestUDPStream|TestUDPMultiNode)' -count=3`,
`go test ./internal/udpproto -count=5`.
[Stage 6 UDP CI](https://github.com/SawaMEN/FoxTunnel/actions/runs/39443565946).

**Ограничение replay:** UDP не содержит обязательных nonce/sequence-id
с end-to-end anti-replay проверкой; одинаковый пакет с уже разрешённым
IP:port может повториться как в настоящем UDP-соединении. Эти изменения
не являются криптографической anti-replay защитой. DNS-ответ для
доменных запросов проверяется как числовой IP с правильным портом,
но клиент не может локально подтвердить DNS-резолюцию на сервере
без изменения протокола.

## Подэтап 4: отключение и восстановление IPv4/IPv6, DNS, exit

В `scripts/test_linux_tun_e2e.py` расширен **настоящий локальный**
netns E2E тест нативного VPN:

1. При активном TUN и nftables guard завершить FoxTunnel HTTPS exit
   `198.18.0.1:8443`; убедиться, что native клиент не завершился
   и что трафик TCP (IPv4), UDP (IPv6), DNS A (IPv4) и DNS AAAA
   (IPv6) не получает ответов по физическому интерфейсу.
2. Запустить новый HTTPS exit с тем же локальным сертификатом;
   повторить TCP, UDP и DNS A/AAAA для обеих семей адресов.
   Проверяется успешное **новое** соединение; старые UDP-сессии
   при реконнекте не переотправляются и не считаются сохранёнными.
3. При работающем клиенте опустить `fcwan0`, проверить отказ
   TCP/UDP/DNS, поднять интерфейс и восстановить адреса и
   физические IPv4/IPv6 default routes; подтвердить возврат
   доступа через TUN и сохранение `policy drop`.
4. Убить дочерний процесс FoxTunnel (SIGKILL), подтвердить, что
   native launcher удалил VPN policy routes, **но оставил**
   отдельный nftables guard. После восстановления физических
   default routes IPv4/IPv6 проверить отрицательные TCP/UDP/DNS
   пробы; затем в **изолированном netns** снять guard и подтвердить,
   что тот же трафик действительно мог бы пройти (положительный
   контроль против ложного PASS из-за отсутствующего маршрута).

В `scripts/test_linux_native_vpn.py` добавлены негативные случаи:
если настройка `resolvectl dns` завершается ошибкой, cleanup
откатывает IPv4/IPv6 правила и вызывает `resolvectl revert`,
не трогая nftables. При уже установленном guard повторная
инициализация launcher отклоняется до изменения маршрутов —
автоматическое небезопасное повторное включение не производится.

`.github/workflows/native-tun-e2e.yml` запускает Python unit
tests и два независимых прогона E2E с уникальными netns.

**Пределы доказательства:** тест проверяет восстановление новых
сеансов после переподключения **удалённого HTTPS exit и локального
физического интерфейса**, но не горячую замену локального
launcher: тот по умолчанию намеренно отклоняет уже установленный
guard и требует контролируемого оператора. Не проверены DoH
через HTTP/443, системный DNS вне изолированной netns,
произвольные сторонние firewall правила, перезагрузка ОС и
сетевые блокировки операторов. Это задачи для отдельных
сетевых и security проверок, не VDS gate.

[Локальный native TUN reconnect E2E](https://github.com/SawaMEN/FoxTunnel/actions/runs/39445085915).

## Подэтап 5: воспроизводимый TUN/UDP/DNS soak (PASS)

`scripts/stage6_tun_soak.py` использует **реальные процессы**
в изолированных Linux netns: native VPN launcher, дочерний FoxTunnel
TUN/gVisor клиент и удалённый локальный HTTPS exit. Вместо заглушки
выполняются настоящие TCP echo, UDP echo, DNS A/AAAA через TUN
по IPv4/IPv6; содержимое ответов проверяет исходный E2E PROBE.

- Два независимых прогона по **25 секунд полезной нагрузки**,
  по **31 итерации** каждый, максимум три одновременных probes,
  интервал между пакетами не менее **0,75 с**. Каждый прогон:
  TCP 62/62, UDP 62/62, DNS A 31/31, DNS AAAA 31/31.
- Контроль каждого процесса через `/proc/<pid>/status`
  (`VmRSS`) и `/proc/<pid>/fd` (FD и socket FD), базовая,
  промежуточные и финальная выборки. Конечная выборка берётся
  **через 34 секунды без нагрузки**, чтобы истекло нормальное
  30-секундное время неактивного UDP flow.
- На каждый процесс установлены пороги: не более **768 МиБ RSS**,
  не более **512 FD** в пике, рост RSS к концу ≤ **128 МиБ**,
  прирост FD ≤ **48** и socket FD ≤ **32**.
- В обоих прогонах клиент достигал пиковых **297 FD**, а после
  cooldown оставалось **9 FD / 2 socket FD**. На сервере было
  до **79 FD**, после cooldown **7 FD / 2 socket FD**.
  Изменение RSS клиента от старта к концу составляло
  около 29–45 МиБ. Превышений бюджетов и неуспешных
  запросов в двух итоговых прогонах не было.
- До исправления первый нагрузочный прогон падал:
  из-за накопления одноразовых DNS UDP associations на
  30-секундном таймауте возникали потери и насыщение 128 UDP slots.
  В `internal/nativetun/linux.go` idle timeout только для
  DNS/UDP 53 уменьшен до **3 секунд**, обычный UDP остался
  **30 секунд**; тест `stage6_udp_idle_test.go` закрепляет поведение.
  Нагрузка также ограничена скоростью, которая не превышает
  расчётный бюджет активных слотов. Это **не** гарантия отсутствия
  потерь при перегрузке выше лимитов.
- В native E2E после нагрузки повторяются сценарии разрыва exit,
  падения дочернего процесса, восстановления линка, DNS и
  проверяются IPv4/IPv6 policy route cleanup и сохранение nft guard.
  Отдельные unit-тесты доказывают, что превышение бюджета приводит
  к падению CI, а не просто записывается в отчёт.

Два агрегированных отчёта доступны как
[artifact `stage6-tun-soak-netns`](https://github.com/SawaMEN/FoxTunnel/actions/runs/39448375868)
в GitHub Actions. Метрики не содержат полезную нагрузку и секреты.

**Ограничения:** 25 секунд нагрузки × 2 — краткая лабораторная
проверка с замерами за ~34 секунды последующей очистки, не часы
непрерывной работы. Счётчики /proc и RSS не доказывают
отсутствие всех утечек памяти, kernel socket state или data races
за пределами проверенных сценариев. Продакшн-DNS, DoH, холодный
старт под блокировками провайдера и тесты через реальные VDS
не проводились.

# Каскадный выход VetroffProxy

По умолчанию сервер VetroffProxy сам открывает соединения к назначениям.
Для каскада включите SOCKS5-выход на **каждом сервере, который завершает
пользовательский туннель**. Само наличие второго узла в списке fallback
не создаёт последовательный каскад.

Схема: клиент → VetroffProxy на первом сервере → SOCKS5 → следующий VPN → интернет.
SOCKS5 может принадлежать ядру панели или локальному клиенту VetroffProxy,
подключённому ко второму серверу. У второго клиента для UDP должны быть включены
`--enable-udp` и, при необходимости, `--udp-stream`; сервер второго узла тоже
должен разрешать UDP. Обычный HTTP CONNECT не является UDP-выходом.

Добавьте в существующий приватный `server.json`:

```json
{
  "egress_proxy": "socks5://127.0.0.1:1080",
  "egress_dns": "1.1.1.1:53"
}
```

Это фрагмент, остальные поля конфигурации сохраняются. Вместо `1.1.1.1:53`
можно указать свой DNS, доступный через следующий узел и поддерживающий TCP.
При отсутствии `egress_dns` используется `1.1.1.1:53`, тоже через SOCKS5.
Проверка конфигурации: `vetroffproxy check-config --config server.json`.

Для запуска без JSON добавьте к существующей команде сервера:

```sh
--egress-proxy socks5://127.0.0.1:1080 --egress-dns 1.1.1.1:53
```

Поддерживается авторизация `socks5://user:password@127.0.0.1:1080` с URL-кодированием
спецсимволов. Пароли лучше хранить в приватном JSON, а не в аргументах процесса.
Прокси и DNS указываются числовыми IP и портами; для IPv6 нужны квадратные скобки.
Это исключает необходимость прямого DNS-запроса для запуска каскада.
SOCKS5 сам по себе не шифрует данные: для удалённого следующего узла используйте
защищённый транспорт или локальный VPN-клиент.

В Go API аналогичные поля: `ServerConfig.EgressProxy` и `ServerConfig.EgressDNS`.
Инициализация конфигурации не открывает сетевые соединения.

| Путь полезной нагрузки | Через выбранный SOCKS5 |
| --- | --- |
| TCP: H2 CONNECT/POST, H3 CONNECT/POST, WSS | Да |
| TCP: XHTTP stream-one, stream-up, packet-up | Да |
| UDP v1 запрос/ответ | Да, UDP ASSOCIATE |
| UDP v2 постоянный поток, несколько назначений | Да, отдельная ассоциация на поток назначения |
| Bonding RPC и persistent lanes | Да, на общем выходном хабе |
| DNS имён назначений | Да, DNS-over-TCP через SOCKS5 |

IPv4 и IPv6 назначения поддерживаются. Запрет приватных и специальных адресов
сохраняется: DNS-ответ проверяется до отправки числового назначения прокси.
Имена разрешаются на выходной стороне каскада, но финальный SOCKS получает
числовой адрес; доменные правила следующего ядра зависят от его sniffing.
DNS из локального hosts-файла может обрабатываться без сетевого запроса.

При отказе прокси, ошибке авторизации, недоступном DNS или отсутствии UDP ASSOCIATE
**прямого fallback нет**. Ошибка завершает соединение или отбрасывает UDP.
SOCKS5 UDP fragmentation не поддерживается; фрагментированные и посторонние
ответы отбрасываются. Адрес UDP-реле в ответе SOCKS должен быть числовым;
нулевой IP заменяется IP прокси. Размер UDP-пакета ограничен накладными расходами
SOCKS5 и доступным MTU. Закрытие TCP-контроля завершает UDP-ассоциацию.

`bond-upstream` — отдельный механизм пересылки bonding к общему хабу,
а не настройка выхода обычных TCP/UDP. Настройте `egress_proxy` на хабе.
Входящие transport-соединения, соединения relay → hub, ответы cover-сайта
и собственный код в пользовательском `Cover` не являются сокетами назначений.
Эта настройка не перехватывает весь сетевой трафик процесса или ОС.

Проверки `TestCascade*` используют локальный SOCKS5 endpoint с авторизацией,
который отвечает внутри прокси без подключения к указанным публичным целям:
TCP по всем восьми транспортам, UDP v1/v2 и IPv4/IPv6, DNS, bonding через relay,
отказ следующего узла и запрет direct fallback. Отдельно проверяются отмена
зависшего handshake, некорректные настройки и отбрасывание чужих UDP-ответов.
Это не проверка развёрнутых серверов пользователя и не интеграция VetroffProxy
в генератор конфигурации конкретной панели.

Дополнительно `TestCascadeFoxTunnelToFoxTunnel` проверяет цепочку двух настоящих
серверов VetroffProxy и локального SOCKS5 клиента второго узла: TCP, UDP v1/v2,
доступную целевую службу и отсутствие direct fallback после остановки следующего
SOCKS5. Все проверки работают локально без доступа к публичным тестовым IP.

Проверка изменений: полный `go test ./... -count=1 -timeout=180s` прошёл на
Go 1.26.10 из `go.mod`; целевые проверки каскада также прошли с `-race`.
`go vet ./...` прошёл. На Go 1.27.3 существующий `TestNativeSetupTimeout`
падает для WSS и трёх режимов XHTTP (`setup request leaked`); тот же результат
воспроизведён на чистом исходном `xfd` (40ef2d0), без изменений каскада.

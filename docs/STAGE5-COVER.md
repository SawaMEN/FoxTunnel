# Stage 5/8 — HTTPS cover и безопасность публичного сайта

**Статус:** подэтапы 1–4 из 5 после прохождения CI. Ветка `up`. Этап 4 остаётся
открытым (1/5). Завершение этого подэтапа не означает завершение
HTTPS-маскировки или устойчивость к DPI.

## Что уже было до этапа 5

- Сервер использует один HTTPS listener для аутентифицированного
  H2/H3/WSS туннеля и обычных HTTP-запросов.
- Приватный трафик поступает на tunneling handler **только после**
  корректного Proxy-Authorization или managed access.
- `Server.cover` не передаёт в публичный обработчик
  `Proxy-Authorization` и заголовки `X-FoxTunnel-*`.
- Локальный `NewCover` не перечисляет каталоги, не обслуживает dotfiles,
  разрешает только GET и HEAD; проверки `CheckPublicRoot` предотвращают
  публикацию явно указанных приватных конфигураций.

## Подэтап 1: запрет symlink alias, целостность ответов

Ранее `os.OpenRoot` защищал от выхода **за пределы** каталога, но
следовал символическим ссылкам **внутри** каталога. Например, файл
`public.txt -> .secret` можно было запросить по обычному имени, не
совпадающему с запрещённым `.secret`.

Теперь `internal/tunnel/cover.go`:

1. Проверяет исходные компоненты URL до `path.Clean`, а также
   все компоненты пути под `os.Root`.
2. Запрещает symlink-компоненты, в том числе вложенные ссылки на
   внутренние dotfiles и конфигурационные файлы.
3. Открывает файл после `Lstat`, сверяет идентичность inode/объекта
   с `os.SameFile` и отдаёт **тот же уже открытый** файловый дескриптор
   через `http.ServeContent`, без повторного открытия в `FileServer`.
4. Сохраняет HEAD, Range/206, content type, обычный index.html
   и HTTP-редиректы `/directory -> /directory/`,
   `/index.html -> ./`.

Это именно защита от случайного размещения ссылок на приватные файлы;
**публичным каталогом должен владеть оператор**. Не давайте недоверенным
пользователям право одновременно записывать/переименовывать содержимое,
не храните в нём секреты и не рассчитывайте на неизменность файлов при
злонамеренном параллельном изменении дерева. Твёрдые ссылки на секреты
внутри публикации тоже недопустимы.

## Проверка

~~~sh
go test -race ./internal/tunnel -run '^(TestStage5|TestCover|TestStage2Cover)' -count=4
go test ./internal/tunnel -run '^TestStage5' -count=20
~~~

Набор `stage5_cover_test.go` проверяет symlink alias, скрытые файлы,
вложенные ссылки, отсутствие листинга и эхо-проб, GET/HEAD, Range,
права доступа и изоляцию приватных заголовков при ошибочной авторизации.

## Подэтап 2: изоляция маршрутов без правильной авторизации

Добавлен `internal/tunnel/stage5_routing_test.go`: матрица
HTTP handler H1/H2/H3 для обычного GET, WebSocket upgrade path,
CONNECT, H2/H3 POST, XHTTP, cluster/bond и UDP, в обоих
вариантах авторизации (legacy и managed).
Запросы без авторизации, с неверным Basic или двумя заголовками
должны направляться в тот же публичный обработчик без секретных
`Proxy-Authorization` / `X-FoxTunnel-*` метаданных.

При **правильной** авторизации и несовместимом padding проверяется
явный отказ 400, а при занятом лимите туннелей — отказ 503 без
исходящего соединения. Также проверяется учёт активных туннелей.

**Пределы проверки:** установка `ProtoMajor=3` в HTTP handler
не заменяет настоящий QUIC/H3-тест. Цель этой подзадачи — доказать
отсутствие случайного обхода авторизации внутри маршрутизатора;
реальный TLS/H3/HTTP network-stack ещё проверяется отдельно в
последнем подэтапе, но только на локальном стенде.

## Подэтап 3: обычная HTTPS-страница по реальному TLS H1/H2

`TestStage5CoverHTTPSConditionalAndCache` запускает сервер на **реальном
loopback TLS-сокете** дважды — с HTTP/1.1 и с согласованным HTTP/2.
Для GET и HEAD проверяются `Content-Type`, `Last-Modified`,
`Content-Length`, отсутствие тела у HEAD; для условного GET с
`If-Modified-Since` ожидается `304 Not Modified`, для `Range` —
`206 Partial Content`, также проверяется канонический редирект и
обычный корневой HTML. Несанкционированные proxy-заголовки не должны
переключать обычный сайт в режим туннеля.

Это реальные HTTP/1.1 и HTTP/2 TLS-запросы, **но не браузерный fingerprint
Firefox**, не проверка cache policy за пределами стандартного
`http.ServeContent` и не H3/QUIC интеграция. Реальный H3 остаётся
задачей локального E2E без VDS.

## Подэтап 4: ограничение параллельных Cover-обработчиков

Публичные GET/HEAD-запросы и отклонённые попытки туннелирования используют
`Server.cover`. Раньше медленный обработчик или большой статический файл
мог поддерживать произвольное количество параллельных обработчиков.
Теперь отдельная атомарная квота `MaxCoverRequests` (значение по умолчанию
**64**, настраивается в `Server` до запуска HTTP listener) ограничивает
количество активных Cover-обработчиков. Она **не связана** с
`MaxTunnels` или счётчиками UDP/хранилища авторизации.

При исчерпании квоты обычные и неавторизованные запросы возвращают
одинаковый `503 Service Unavailable` с `Retry-After: 1` и
`Cache-Control: no-store`; нельзя кэшировать ответ перегрузки как
обычную публичную страницу. Освобождение слота сделано через `defer`
при обычном завершении, отмене контекста и panic пользовательского
Cover-обработчика.

`TestStage5CoverConcurrencyBudgetAndTunnelIsolation` создаёт
блокирующие запросы и параллельный всплеск из 64 посетителей в обоих
вариантах авторизации; проверяет, что лишние вызовы Cover не попадают
в обработчик, не влияют на `activeTunnels` и что квота восстанавливается.
`TestStage5CoverBudgetOverRealTLS` повторяет сценарий на реальном
локальном HTTP/1.1 и HTTP/2 TLS listener. Дополнительно проверены
отмена и panic без утечек слотов, есть локальный microbenchmark
`BenchmarkStage5PublicCoverAdmission`.

Это лимит **одновременно обрабатываемых HTTP-запросов**, а не
ограничение полосы, размера файлов, скорости приёма новых TLS handshakes
или защита от всех вариантов DoS. `MaxTunnels`, ограничения listener,
TLS handshake timeout и сетевые лимиты сервера необходимо настраивать
отдельно. Результаты CI являются лабораторными, реальные VDS не нужны.

## План: пять подзадач

- [x] Зафиксировать существующие границы HTTPS tunnel/cover;
  устранить symlink alias, сохранить корректную публичную статику.
- [x] Проверить HTTP-обработчик для H1/H2/H3 и WSS/CONNECT/POST/XHTTP
  при неверной авторизации; отдельно проверить padding и лимит туннелей
  после правильной авторизации. Для H3 это пока тест маршрутизации
  ProtoMajor=3, а не настоящий QUIC wire-тест.
- [x] Проверить обычные GET/HEAD, redirect, условный HTTP-кэш и
  `Range` на реальном локальном TLS H1/H2 сервере. Браузерная
  идентичность Firefox не утверждается.
- [x] Ввести независимую от туннелей квоту параллельных Cover-вызовов,
  проверить перегрузку, отмену и локальные TLS H1/H2 запросы. Это не
  сетевой bandwidth limiter и не защита от всех DoS-сценариев.
- [ ] Подтвердить публичный HTTPS cover и авторизованный туннель в
  локальном E2E-стенде TLS H1/H2/H3 со сбором тестовых захватов и проверкой
  завершения соединений. VDS не требуется.

**Полное поведенческое совпадение с Firefox/Necko, маскировка QUIC
и обход фильтрации этим изменением не доказаны.**

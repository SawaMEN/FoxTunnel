# Главная нода и единая ссылка

**Русский** · [English](CLUSTER.en.md) · [Каталог](../README.md)

> **Назначение:** Входные ноды, доверие к ним, discovery и выходная нода.

Главная нода одновременно выдаёт состав кластера и является общим выходом:
здесь блоки всех входных путей собираются в один TCP-сеанс назначения.
В `vetroff://` достаточно адреса главной ноды, `bond: true` и `discover: true`.
Адреса входов хранятся на главной ноде, а клиент получает их после авторизации
по проверенному TLS 1.3/H2. Клиент затем подключается непосредственно к входам.
Один адрес в ссылке не означает, что все пакеты идут через один вход.

## Настройка главной ноды

Автоматическая подготовка и присоединение входов: [setup / cluster-add](../guides/SETUP.md).
У каждой записи также могут быть `sni` и `pin_sha256`; `setup` вычисляет их в
публичном `node.json`. Клиент проверяет CA/имя и дополнительный pin независимо
для каждого входа. Политика главной ноды не подставляется другим адресам.

Создайте `cluster.json` с собственными доверенными входными нодами:

```json
{
  "v": 1,
  "nodes": [
    {"url": "https://node-a.example", "weight": 4},
    {"url": "https://node-b.example", "weight": 1},
    {"url": "https://node-c.example", "weight": 2, "disabled": true}
  ]
}
```

На главной ноде:

```sh
./foxtunnel server --listen :443 --cert main.crt --key main.key \
  --web-root /srv/public-site --bond-hub --cluster-file cluster.json
```

На каждой входной ноде:

```sh
./foxtunnel server --listen :443 --cert node.crt --key node.key \
  --web-root /srv/public-site --bond-upstream https://main.example
```

Во всех процессах нужны одинаковые `FOXTUNNEL_USER` и `FOXTUNNEL_PASSWORD`.
Сертификаты должны соответствовать адресам. Для частного CA у входов есть
`--bond-ca-cert`, у клиента — `--ca-cert`. NSS включается на клиенте через
`--tls-backend nss` в сборке с поддержкой NSS; вход → главная нода использует Go TLS.

Можно включить саму главную ноду в `nodes`, если клиенту нужен прямой путь к ней.
Иначе она обслуживает только управление и выход для этих сессий.
Допустимо до восьми записей, включая отключённые; нужна хотя бы одна включённая.
Одна включённая нода — режим деградации, без суммирования нескольких путей.

## Ссылка и подключение

```sh
umask 077
./foxtunnel share --server https://main.example --bond --discover > connection.txt
./foxtunnel client --link-file connection.txt
```

Либо непосредственно:

```sh
./foxtunnel client --server https://main.example --bond --discover
```

Ссылка содержит один адрес и секретные учётные данные. `--discover` требует
`--bond`, не сочетается с `--fallback-server` или `--padding`. Для старых клиентов
новое поле `discover` неизвестно: они отклонят такую ссылку. Явный список входов
и прежние ссылки продолжают работать без discovery.

## Распределение и изменения состава

`weight` — относительная мощность от 1 до 100, заданная администратором.
Планировщик оценивает `(текущие запросы + 1) × EWMA времени обмена / weight`.
Неизвестный путь получает пробу по требованию; после ошибки действует прежняя
пауза в пять секунд. Начальная позиция выбирается случайно, чтобы новые клиенты
не начинали все с первого входа.
Поэтому вес 4 не гарантирует ровно 80% байтов при весе
другого пути 1: влияют скорость, длительность ожидания, занятость и отказы.
Пустые long-poll ответы не увеличивают оценку времени обмена.

Веса и список меняются атомарной заменой файла на главной ноде. Она перечитывает
его при авторизованном запросе состава. Клиент обновляет снимок по требованию
нового соединения раз в 30 секунд; одновременные обновления объединяются.
Неизменный состав сохраняет накопленные измерения. Новый состав применяется к
новым сессиям, существующие сохраняют свои пути и порядок данных. Для вывода
ноды из эксплуатации сначала исключите её и дождитесь завершения старых сессий.

Выдаваемый снимок действует 120 секунд. При временной сетевой ошибке или
408/429/503/504 разрешено использовать ещё действующий снимок. После истечения
срока новые сессии требуют успешного обновления. Ошибки TLS, авторизации,
редиректы, HTTP/1 и неверный JSON не разрешают откат к старому снимку.
При первом запуске главная нода обязательно должна быть доступна.

Состав содержит идентификатор процесса общего выхода. Клиент предъявляет его
уже при открытии сессии: ошибочно настроенный вход с другим выходом отклоняется
до подключения к назначению. Все входы доверенные, TLS завершается на каждом;
главная нода делегирует им получение тех же учётных данных. Редиректы и
непроверенный TLS не используются.

## Границы реализации

Главная нода централизует состав и сборку, но пока не собирает телеметрию CPU,
полосы и занятости всех входов. Решения по запросам принимает клиент по своим
измерениям; `--max-tunnels` ограничивает нагрузку на каждом сервере, а 503
включает повтор через альтернативу. Автоматического глобального распределения
между всеми пользователями и автоматического вычисления весов ещё нет.

Главная нода остаётся общей точкой отказа и ограничения полосы. Отказ входа
покрывается другим входом; отказ главной ноды не сохраняет её TCP-сокеты.
Формат передачи блоков остаётся HTTP RPC; постоянные каналы, H3/UDP и DNS-режим
не входят в это изменение. Польза против ТСПУ требует полевых измерений.

Проверены Go/NSS: одна главная нода, два входа, SOCKS5, потерянный ответ открытия,
потерянный ACK, отказ входа во время передачи, целостность и полузакрытие одного
TCP-сеанса. Отдельно проверены веса 4:1 при одинаковой задержке и накопленной
нагрузке, cooldown, обновление/истечение снимка, скрытие состава без авторизации,
ограничения JSON и фаззинг. См. [объединение](BONDING.md).

# Экспериментальный UDP ASSOCIATE (этап 1)

**Русский** | [English](UDP.en.md) · [Документация](../README.md)

FoxTunnel поддерживает **опциональный** SOCKS5 UDP ASSOCIATE (RFC 1928) с доставкой одной небольшой UDP-датаграммы по авторизованному HTTPS POST и возвратом **первого** UDP-ответа. Это **не полноценный UDP VPN**: нет TUN, NAT-сессий, непрерывной приёмной стороны, QUIC datagram, multicast, фрагментации или гарантии для звонков/игр. Цель — функциональный защищённый запрос/ответ, например обычный DNS, без изменения существующих TCP-конфигураций.

## Включение

На сервере, созданном без `setup`: `foxtunnel server ... --enable-udp`. При развёртывании через `setup` задайте `foxtunnel setup ... --enable-udp`; свойство `enable_udp` попадёт в защищённый `server.json`. Клиенту нужно отдельно передать `foxtunnel client --enable-udp ...`; этот флаг допускается вместе с `--link-file`, но **никогда не кодируется** в ссылке `vetroff://`. В публичном SDK используются `ClientConfig.EnableUDP` и `ServerConfig.EnableUDP`. Значение по умолчанию — **false на обеих сторонах**.

`--enable-udp` клиента несовместим с `--bond`/discovery в этом этапе. Для H3 также нужен работающий UDP listener транспорта. Прокси SOCKS5 по-прежнему должен слушать **только loopback**: для него нет отдельной аутентификации.


## Этап 2: постоянный мультиплексированный UDP-поток (opt-in)

Команда клиента `foxtunnel client --enable-udp --udp-stream ...` выбирает **отдельный** HTTPS endpoint `/.well-known/foxtunnel-udp-stream-v2`. На сервере достаточно существующего `--enable-udp`. В Go SDK — `ClientConfig{EnableUDP: true, UDPStreaming: true}`. Флаг `--udp-stream` без `--enable-udp` отклоняется.

Каждая SOCKS5 UDP ASSOCIATE устанавливает **один длительный HTTP/2 (или HTTP/3) POST с двусторонним телом**. Датаграммы передаются как `uint16 length (big-endian) + валидный SOCKS5 UDP packet` (максимум 1232 байта), без фрагментации или незаметного перехода обратно на v1. Несколько адресов назначения передаются по одному потоку. Сервер поддерживает **до 16 независимых pinned UDP-сокетов** на одну ассоциацию; в отличие от этапа 1 один запрос теперь может получить **несколько асинхронных ответов**.

Границы ресурсов: максимальное время жизни потока **10 минут**, тайм-аут неактивного UDP-сокета **30 секунд**, исходящая очередь ответов **32 пакета**; при переполнении пакеты отбрасываются, при полном числе назначений вытесняется самое старое. Локальный UDP-источник фиксируется по IP и порту после первой валидной датаграммы, жизнь ассоциации ограничена TCP control-сокетом. Входящий HTTP проверяет авторизацию и использует `MaxTunnels`, серверный DNS/IP-фильтр, pinning и учёт трафика через access. Изменение версии требует явного переключения и совместимого сервера.

Это **экспериментальный UDP поверх надёжного HTTP-потока**: при потерях возникает head-of-line blocking, возможна дополнительная задержка. Нет UDP/QUIC DATAGRAM, TUN, системного DNS, NAT-миграции, мульткаста, гарантии работы звонков/игр или обхода ТСПУ. До реальных полевых испытаний и нагрузочных замеров не считать режим production-ready.

Тесты: `go test ./internal/udpproto ./internal/tunnel -run 'TestUDP|TestStream' -count=1` и `go test -race ./internal/udpproto ./internal/tunnel`. Проверяются мультиплексирование разных UDP-выходов, несколько ответов на одну датаграмму, ограничения формата, закрытые по умолчанию endpoints и обычный v1.

## Защита и формат

- Только SOCKS5 UDP ASSOCIATE, только 1 TCP-контрольный сокет и его UDP-источник. UDP-пакеты принимаются только от того же IP; порт закрепляется первым валидным пакетом. При закрытии TCP контроля UDP-сокет закрывается.
- Одна датаграмма — один независимый HTTPS POST на `/.well-known/foxtunnel-udp-v1`. Снаружи остаются CA/SNI/SPKI проверки выбранного транспорта и Basic/access-аутентификация **внутри TLS**. Прямая HTTP/1.1 доставка не разрешается.
- Размер SOCKS5 UDP-пакета (включая RFC 1928 заголовок) до **1232 байт**; FRAG должен быть 0. Пакеты с неверным RSV/ATYP/адресом, нулевым портом или превышением размера отклоняются. Лимит **8** одновременных запросов на одну ассоциацию.
- Сервер использует ограничения `max-tunnels`, существующие квоты и политику запрещённых адресов. DNS производится на сервере, адрес фильтруется и закрепляется **до UDP dial**: защита от DNS rebinding не ослабляется. `--allow-private` оставляйте выключенным для публичного сервера.
- Сервер ждёт только **первый** ответ в пределах 3 секунд (или меньшего `DialTimeout`). Нет ответа — HTTP 204; клиент не посылает UDP-пакет в ответ. При ошибке запроса никакого второго сервера не пробуется; нет replay на другом выходе.
- Relay UDP-ответов ограничен тем же адресом и портом назначения; сетевой UDP-сокет connected. Не используется синтетический padding ради сходства с Firefox.

## Самопроверка

```bash
go test ./internal/udpproto ./internal/tunnel -run 'TestUDP|TestMalformedPackets|TestRoundTrip' -count=1
go test -race ./internal/udpproto ./internal/tunnel
```

Интеграционный тест проверяет SOCKS5 UDP ASSOCIATE → HTTPS/H2 → локальный UDP echo и отказ по умолчанию; это **не** тест реальных операторов. Для реальных UDP-приложений следующий этап — persistent association, flow-controlled multiplexing, независимые лимиты UDP и TUN/DNS/kill switch. До этого не обещать превосходство над VLESS.

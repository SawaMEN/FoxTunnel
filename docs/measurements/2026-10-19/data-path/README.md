# Измерения передачи / Data-path measurements

[Измерения](../../README.md) · [Исследования](../../../research/README.md)

> **Исторические замеры.** Сохраняйте исходные записи и воспроизводимые параметры; loopback не равен реальной сети.

Сценарии, ограничения и команды: [RU](../../../research/DATA-PATH.md) /
[EN](../../../research/DATA-PATH.en.md).

Go 1.26.9, Linux amd64, Intel Xeon Platinum 8573C; общий runner. NSS 3.130 из
закреплённого Firefox 158.0. Профиль TLS Mozilla не включается в этих опытах:
проверяется стандартный NSS backend и транспорт bond.

`record-link.txt`: два проверенных H2/TLS-входа, один hub в том же процессе,
1 МиБ echo, восемь блоков, по 20 обменов и три повторения. `recordRTT20ms` —
по 10 мс до обработки записи и перед её ответом. `ACKloss17` — потеря первого
успешного upload ACK для номеров, кратных 17, через сброс HTTP-потока.
Это не netem/TCP packet loss. CPU/аллокации модели включены в измерение.

`relay-go-nss.txt`: тот же бинарный файл с NSS, настоящий SOCKS, два HTTPS-relay,
отдельный HTTPS-выход и TCP echo. Клиент Go или NSS; relay использует стандартный
NSS backend этой сборки. Записи приложения 137 байт или 32 КиБ. По три повторения
500 мс. Установка SOCKS/сессии исключена; создание каналов входит в измерение.
`cgo/op` — переходы Go/C всего процесса, включая relay. Это не нативная память.

p95 — nearest-rank процентиль полного echo; малая выборка не даёт устойчивой
оценки хвоста. B/op и allocs/op суммируют все горутины/серверы/модель; это не
одновременно занятая память. CPU-us/op — process user+system CPU. process-peak-KiB —
кумулятивный high-water RSS процесса; последующие случаи наследуют прежний пик.
Его нельзя сравнивать как RSS отдельных режимов или native-память одной сессии.

Профили `nss-rpc-cpu.txt`, `nss-lanes-cpu.txt`, `nss-rpc-alloc.txt`,
`nss-lanes-alloc.txt` — отдельные прогоны по три секунды для NSS/32 КиБ. Исходные
pprof-бинарники используются временно; опубликован текстовый top без содержимого
трафика. Native NSS-стеки и все C-аллокации этими профилями не измерены.

На модели уменьшаются HTTP/аллокации; диапазоны скорости с задержкой и потерей
ACK перекрываются. Даже новый режим не держит ровно 16 запросов навсегда:
адаптация выбора входа/пула, poll/EOF и повторы открывают новые каналы.

Число аллокаций меньше, но выделенные байты/cgo не всегда ниже. Go bulk через
relay в этой выборке **медленнее**; NSS сильно варьируется. Это причина оставить
новые каналы за локальным `--bond-lanes`, а обычный `--bond` — на RPC. Общее
ускорение, меньшая память NSS и улучшение Интернета не установлены.

Профили показывают syscall/cgo как крупные расходы обоих режимов. У lanes
заметен memmove (7,58% flat в этом профиле), а `Hub.serveLane` даёт 54,58%
выделенных Go-байтов; у RPC `readBoundedInto` — 37,43%. Полные суммы двух pprof
не сравниваются: у прогонов разное число обменов и длительность. Следующая
оптимизация — безопасное повторное использование server record buffers с
сохранением владения после потерянного ACK и меньшая перестройка пула входов.

The implementation is deliberately opt-in (`--bond-lanes`). Fewer HTTP requests
and allocations do not establish a universal throughput or memory improvement.
The real Go bulk relay workload regressed; delayed/ACK-loss throughput ranges
overlap, and NSS results vary widely. Packet loss and field performance remain
unmeasured. The detailed reports preserve adverse results as well as wins.

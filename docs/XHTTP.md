# XHTTP и Mozilla NSS

**Русский** | [English](XHTTP.en.md)

Встроенный транспорт не запускает Xray и не импортирует его код. На клиенте
можно выбрать TLS Mozilla NSS; HTTP/2 при этом реализован Go. Использование NSS
не означает совпадение ClientHello и полного сетевого поведения Firefox.
Сервер завершает TLS средствами Go. Второго TLS-слоя внутри carrier нет.

## Быстрый запуск

Соберите клиент с `go build -tags nss ./cmd/foxtunnel` (Linux, NSS/NSPR и cgo),
затем создайте настройки с действующим сертификатом:

```sh
./foxtunnel setup --server https://main.example \
  --cert /etc/certs/main/fullchain.pem --key /etc/certs/main/key.pem \
  --transport xhttp-stream-up --tls-backend nss --out main-node
./foxtunnel server --config main-node/server.json
./foxtunnel client --link-file main-node/connection.txt
```

`setup` создаёт случайный секрет, проверяет сертификат и записывает готовую
`vetroff://` ссылку в закрытый файл. SNI, SPKI pin и транспорт сохраняются в ссылке.
Для второго потокового режима замените транспорт на `xhttp-stream-one`.
Для пакетной отправки используйте `--transport xhttp-packet-up`.
Без NSS используется явный `--tls-backend go`; автоматического отката нет.
Старый сервер необходимо обновить: прежний H2 POST не реализует новый carrier.

## Реализованный формат

| Режим | Отправка | Получение |
|---|---|---|
| `xhttp-stream-one` | POST `/.well-known/vetroff-xhttp/` | Ответ этого POST |
| `xhttp-stream-up` | POST `/.well-known/vetroff-xhttp/<UUID>` | GET по тому же адресу |
| `xhttp-packet-up` | POST `/.well-known/vetroff-xhttp/<UUID>/<seq>` | GET без номера seq |

UUID генерируется случайно для каждого внешнего канала. Потоковый POST имеет тип
`application/grpc`, ответ получения — `text/event-stream`. Это заголовки,
не gRPC-фрейминг и не SSE-кодирование полезных данных. Запросы имеют случайное
дополнение в Referer, ответы — X-Padding (100–1000 символов). Кэширование и
буферизация ответа явно отключены. Неиспользуемый ответ upload в `stream-up`
получает дополнение раз в 25 секунд; оно не входит в поток приложения.
Внешний ALPN — `h2`; HTTP/1.1 и HTTP/3 для этих carriers пока не поддержаны.

В `packet-up` POST имеет известную длину и тип `application/octet-stream`. Клиент
читает блоки до 32 КиБ и ждёт ACK каждого POST после передачи блока во внутренний
поток; автоматического повторения POST
нет. Это ограничивает исходящий конвейер одним блоком и скорость при большом RTT.
Сервер допускает до восьми зарезервированных блоков размером до 64 КиБ каждый,
включая незавершённые чтения и блок, ожидающий потребителя. Блоки собираются по
номеру, начиная с нуля. Повторы, номера вне окна и попытка смешать packet/stream
в одной сессии отклоняются. Пропуск блока или зависшее чтение POST закрывают канал
через 30 секунд; доставка корректного блока сбрасывает таймер пропуска.
Потеря/ошибка ACK закрывает внешний канал, без повторной вставки принятых байтов.
В bond восстановление RPC остаётся задачей уровня сессии FoxTunnel.

Внутри carrier работает мультиплексированный HTTP/2 FoxTunnel: обычные соединения,
discovery и bond. Максимум 32 внутренних потока. Авторизация проверяется как
перед созданием carrier, так и на внутренних запросах; неизвестные/неавторизованные
внешние запросы используют публичный сайт. Как и у существующего WSS, заголовок
`Proxy-Authorization` должен доходить до сервера; обратный прокси может его удалять.

Число внешних сессий ограничено `max-tunnels` (по умолчанию 256), независимо от
лимита активных запросов FoxTunnel. Непарные POST/GET удаляются через 30 секунд.
Повторное присоединение той же стороны отклоняется. Данные проходят через трубы
с обратным давлением, без неограниченной очереди в памяти. В потоковых режимах отмена любого из двух
запросов закрывает пару, внутренний H2 и сокеты назначения. Закрытие idle-клиента
освобождает внешний carrier; запрос закрытия не прерывает ещё активные потоки.

## Граница готовности

Реализованы **три режима с базовой формой запросов XHTTP**, а не полный
набор настроек Xray XHTTP. XMUX, пользовательский путь и отдельный
HTTP Host, разные адреса/транспорты отправки и получения остаются следующими
этапами. VLESS в поток не добавляется. Совместимость с другим XHTTP-клиентом без
FoxTunnel не заявляется; ещё нужны независимые транспортные тесты с эталоном.

Локально проверяются большие данные, полузакрытие, отмена, лимиты, удаление
непарных сессий, очередь/перестановку/повтор/размер packet-up и потерю ACK, CA/SNI/pin до авторизации, ссылки, setup, discovery, потери ACK
и отказ входной ноды. Это не доказывает доступность через CDN или операторов РФ.

Основа независимой реализации: [описание разработчика XHTTP, STREAM-UP/ONE](https://github.com/XTLS/Xray-core/discussions/4113),
[сервер эталона](https://github.com/XTLS/Xray-core/blob/main/transport/internet/splithttp/hub.go).

## Короткий локальный замер

Go 1.26.9, Linux amd64 / AMD EPYC 9V74, Go TLS, один существующий SOCKS-поток,
1 МиБ echo, без bond/padding, два прогона по 300 мс:

| Режим | Полезная скорость, МБ/с | Выделения на операцию |
|---|---:|---:|
| H2 CONNECT | 257–308 | 614–616 |
| XHTTP stream-one | 145–183 | 1860–1882 |
| XHTTP stream-up | 202–203 | 1832–1846 |

Команда: `go test ./internal/tunnel -run '^$' -bench 'BenchmarkNativeTransports/(h2-connect|xhttp)/1MiB' -benchtime=300ms -count=2`.
В этом коротком тесте вложенное HTTP/2-кадрирование увеличивает расходы; ускорение
относительно CONNECT не получено. Это loopback, не Интернет, не NSS и не РФ.

После добавления `packet-up` отдельный короткий прогон этой же методики дал
10,2–12,8 МБ/с и около 5,1–5,2 МБ выделенной памяти на 1 МиБ обмена.
Это консервативный режим: один POST в полёте, ACK после доставки, отдельные
HTTP-заголовки на блок. Для высокой скорости ещё нужны ограниченный конвейер
и объединение мелких записей; эти результаты не заменяют полевые измерения.

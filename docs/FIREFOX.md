# Firefox transport branch

[Главная](../README.md) · [Настройки](FEATURES.md)

Цель ветки `firefox` — передавать TCP через CONNECT в HTTP/2 и HTTP/3,
используя сетевую реализацию Mozilla. Подготовлена отдельная экспериментальная
поставка полного Necko для Linux amd64, проверенная на контролируемом стенде.
Наличие NSS или Neqo само по себе не означает совпадение с Firefox.

Текущая квалификация ветки `xfd`: **5 из 6 этапов**. Нативные SNI/SPKI,
пины отдельных узлов, TLS/H2-профили и интеграция CLI/SDK прошли проверки
на Linux AMD64 и ARM64. [Результаты этапа 5](../experiments/firefox-necko/validation/identity/README.md).
Остался этап 6 — единые релизные архивы NSS + Necko. Опубликованные поставки
этим отчётом не обновляются.

## Первоначальная отдельная поставка Linux amd64: 4 из 4 этапов

1. **CONNECT для обоих транспортов.** Существующий `h2-connect` сохранён;
   добавлен `h3-connect` в CLI, SDK, ссылки и генератор конфигурации. Go backend
   отправляет классический H3 CONNECT. Neqo backend вызывает `Http3Client::connect`,
   поскольку `fetch` отвергает этот метод. Адаптер POST не используется.
   Для Neqo закреплён патч классификации classic CONNECT: закрытие отправки
   сохраняет принимающую сторону. Сборщик проверяет исходный и исправленный
   файлы по SHA-256 и применяет патч в отдельном Cargo home; он также входит
   в provenance сборки. Не используйте непатченный Neqo для этого режима.
   Локальные Go/race-тесты проверяют реальный H3-запрос, данные, half-close,
   отмену и проверку доверия до авторизации. Нативные тесты запускает
   существующий workflow `neqo-experiment.yml`; результат нужно проверять
   для точного коммита этой ветки.
2. **Полный Necko — реализован.** Закреплённый Gecko собран с проверяемыми
   патчами; клиент использует его сетевой стек для классического CONNECT
   через H2 и H3. Полный нативный набор прошёл три раза с `-race`: холодный
   запуск, бинарные данные, half-close в обе стороны, передача через малые
   окна потока, проверка сертификатов до авторизации, 12 одновременных
   туннелей, отмена и восстановление после тайм-аута, отсутствие TCP fallback
   для явно выбранного H3. Хеши runtime и source lock сверены.
   [Результаты проверки](../experiments/firefox-necko/validation/native-0fc7192.json)
   и [журнал](../experiments/firefox-necko/validation/native-0fc7192.log).
   [Повторная сборка и нативные проверки CI](https://github.com/SawaMEN/FoxTunnel/actions/runs/39912988779)
   также прошли успешно.
   Прототип остаётся в
   [experiments/firefox-necko](../experiments/firefox-necko/README.md),
   отдельно от основной поставки CLI и SDK.
3. **Сравнение с Firefox — выполнено для закреплённого runtime.** Полный
   процесс Firefox и xpcshell-адаптер проверены на одном libxul/NSS, одном
   прокси и одинаковом бинарном CONNECT-сценарии: холодный запуск, повторное
   использование соединения, принудительное переподключение с сохранением
   TLS-кеша, FIN. Каждый транспорт измерен три раза. Сохранены ClientHello,
   ALPN, H2 SETTINGS/HPACK, QUIC/H3, возобновление сессий и различия.
   Исправлен обнаруженный User-Agent xpcshell; после этого измеренные поля
   H2 совпали в исходном измерении этапа 3. При повторной проверке этапа 4
   в отдельных H2-прогонах различались raw HPACK, размеры HEADERS и
   порядок SETTINGS ACK относительно HEADERS/WINDOW_UPDATE;
   декодированные заголовки совпали. В H3 совпали состав расширений
   и остальные измеренные поля,
   но порядок TLS-расширений и JA3 различается: оба клиента меняют порядок
   между запусками. H3 возобновил сессию у обоих; H2 в этом стенде — нет.
   Эталон вызывает нативный CONNECT API из Firefox, а не обычную навигацию.
   [Методика, ограничения и результаты](../experiments/firefox-necko/validation/stage3/README.md).
   Это не доказательство неотличимости от обычного браузерного трафика или
   обхода DPI; прототип по-прежнему отделён от основной поставки.
4. **Эксплуатационная проверка — выполнена на Linux amd64.** Пятиминутная
   нагрузка каждого транспорта прошла локально и в CI с проверкой всех байтов,
   CPU, RSS, дескрипторов и стоимости GC/CC. Ограничены idle-сессии, активные
   соединения и удерживаемые native drains; проверено освобождение лимитов.
   Исправлены вызовы native Close с неверного потока, утечка bootstrap-слота
   H2 и задержка освобождения JS/XPCOM-объектов при churn.
   Контролируемый обрыв пути завершается в пределах тайм-аута; после
   восстановления новый CONNECT работает в том же helper. H3 сохраняет
   поток при NAT source-port rebinding. Прерванные потоки автоматически
   не повторяются.
   Отдельный launcher поставляется с полным runtime, provenance, патчами,
   лицензиями и проверяемым manifest; несовместимые версии и повреждённые
   файлы отвергаются. Реальная передача H2/H3 и SIGTERM проверены из пакета.
   [Измерения и ограничения](../experiments/firefox-necko/validation/stage4/README.md),
   [запуск, обновление и откат](../experiments/firefox-necko/OPERATIONS.md).
   Necko подключён к основному CLI/SDK через `--engine necko` и
   `ClientConfig.Engine = "necko"`. Основной клиент сам запускает helper и
   завершает его при закрытии. [Запуск и ограничения интеграции](../experiments/firefox-necko/INTEGRATION.md). Смена IP прокси, IPv4/IPv6, мобильная сеть и многодневная работа
   требуют отдельного пилота; неотличимость от браузера не заявляется.

## Использование CONNECT сейчас

В обычной Go-сборке:

```sh
./foxtunnel setup --transport h3-connect \
  --server https://vpn.example.com --cert /path/fullchain.pem \
  --key /path/privkey.pem --out server-config
./foxtunnel server --config server-config/server.json
./foxtunnel client --link-file server-config/connection.txt
```

На сервере должны быть доступны TCP и UDP на указанном порту. Генератор
включает H3-слушатель для `h3-connect`, как и для `h3-post`.

В сборке `-tags nss,neqo` явно выбирайте Mozilla backend:

```sh
./foxtunnel client --server https://vpn.example.com \
  --engine mozilla --transport h3-connect --h3-fallback none
```

Логин и пароль задаются через `FOXTUNNEL_USER` и `FOXTUNNEL_PASSWORD`.
Этот режим использует Mozilla Neqo/NSS для H3. В режиме `--engine mozilla`
HTTP/2 формирует Go поверх NSS. Полный стек Mozilla для H2 и H3 выбирается
через `--engine necko`; см. [инструкцию интеграции](../experiments/firefox-necko/INTEGRATION.md). Выбор `--h3-fallback h2` разрешает существующий проверяемый H2
fallback только до отправки запроса; это не полный Necko и не повтор
прерванной передачи. Автоматический выбор транспорта пока сохраняет прежние
настройки, поэтому `h3-connect` нужно указывать явно.

Ссылка с `h3-connect` требует клиента из этой ветки: старый клиент отвергнет
новое имя транспорта. Сервер уже обрабатывает классический H3 CONNECT теми же
правилами авторизации, назначения, квот и ограничения ресурсов, что и H2.

# Нативный Linux TUN (экспериментальный Go TCP/IP)

**Русский** · [English](NATIVE-LINUX-TUN.en.md) · [План](../planning/ROADMAP.md)

Новая экспериментальная опция `foxtunnel client --tun ftun0` открывает Linux TUN непосредственно в процессе **FoxTunnel**. Пакеты IPv4/IPv6 разбирает встроенный Go-стек gVisor (библиотека tun2socks/v2 core, MIT), TCP и UDP переправляются в **локальный SOCKS5 того же процесса**, а далее проходят обычную авторизованную TLS-доставку FoxTunnel. **sing-box не требуется**.

## Запуск на отдельном тестовом Linux-хосте

Требуются `/dev/net/tun` и CAP_NET_ADMIN, исправное DNS/TLS-подключение к числовому IP сервера, защищённый SNI/CA или SPKI pin, `--enable-udp --udp-stream`. На сервере UDP тоже должен быть разрешён. При запуске `--tun` отклоняются неподдерживаемый `--bond` и выключенный UDP v2. Клиентский SOCKS5 должен слушать **loopback**, обычно 127.0.0.1:1080.

~~~sh
foxtunnel client --link-file connection.txt --enable-udp --udp-stream --tun ftun0 --tun-mtu 1400
~~~

**Запуск НЕ изменяет таблицы маршрутов, системный DNS и firewall.** На тестовом Linux в отдельном network namespace настройте адреса и маршруты: назначьте `172.28.247.1/30` и `fdfe:dcba:9876::1/126` интерфейсу `ftun0` и направьте default IPv4/IPv6 через него. Обязательно сохраните отдельный маршрут к серверному IP через физический интерфейс; иначе получится рекурсия (сам FoxTunnel уйдёт в собственный TUN). Перед добавлением default route должна действовать fail-closed политика nftables: только loopback, TUN и явно разрешённые серверные IP/порты на физическом интерфейсе. [Linux TUN companion](LINUX-TUN.md) включает генератор такой политики `killswitch.nft`; **не запускайте `run.sh` companion**, он предназначен для отдельного sing-box.

Для диагностики пользуйтесь **локальной консолью**, не SSH: ограничительный firewall может полностью оборвать доступ. Утечки после перезагрузки требуют постоянного firewall; текущий демон его сам не устанавливает. При отключении сервера nftables guard должен оставаться активным.

## Границы реализации

- Подключаются IPv4 и IPv6, TCP/UDP; TCP ограничен до **256 потоков**, UDP до **128 сессий** с ограничением **30 секунд простоя**. Входной MTU разрешён 1280–9000 байт; UDP v2 внутри FoxTunnel по-прежнему принимает не более 1232 байт полного SOCKS UDP-пакета и может отбрасывать большие датаграммы. Большие UDP-пакеты и фрагментация пока не поддерживаются полностью.
- В отличие от sing-box `dns_mode=hijack`, **нативный режим не перехватывает DNS-запросы автоматически**. Для удалённого DNS ОС должна обращаться к числовому IP резолвера через TUN; локальные DNS-stub, DoH и systemd-resolved требуют отдельной настройки. nftables guard блокирует прямой физический DNS, но не гарантирует работу системного резолвера.
- Маршруты, сеть и kill switch — отдельная политика хоста. Многосетевой failover, QUIC DATAGRAM, ICMP, IPv6 extension headers, длительные нагрузки и полевые испытания ещё не сертифицированы. Никакой гарантии устойчивости к ТСПУ нет.
- Библиотека gVisor — нативно компилируемый Go TCP/IP стек, но не написана авторами FoxTunnel с нуля. `tun2socks/v2` используется **как библиотека внутри FoxTunnel**, отдельный бинарный процесс не запускается.

## Испытания

[Workflow Native FoxTunnel Linux TUN](https://github.com/SawaMEN/FoxTunnel/actions/workflows/native-tun-e2e.yml) собирает FoxTunnel со встроенным TCP/IP-стеком, запускает его в новых Linux network namespace, проверяет TCP IPv4/IPv6, UDP, DNS на настоящем тестовом выходе, отказ при остановке клиента, сохранение firewall после закрытия TUN и краткую смену интерфейса. **Пока CI не пройден, нативный режим не считается готовым: прогресс третьего этапа 6 из 7.**

~~~sh
go test ./internal/nativetun
~~~

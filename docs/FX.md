# FX: анализ Firefox fingerprint и снижение аллокаций Necko

Ветка `fx` развивает два направления: обнаружение устойчивых отличий от
Firefox и снижение нагрузки на память при передаче через Necko. Это не новый
сетевой протокол и не гарантированный обход DPI.

## 1. Контроль fingerprint (опциональный строгий gate)

Из существующих тестов сохраняются независимые отчёты:
- `compare_necko_firefox.py`: FoxTunnel против Firefox CONNECT;
- `analyze_firefox_self.py`: контроль Firefox против Firefox на том же runtime;
- `evaluate_fx_fingerprint.py`: классификация отличий с учётом вариативности
  Firefox. Неодинаковые поля **никогда** не нормализуются до «равно».

Пример после получения штатных замеров:

```sh
python3 scripts/evaluate_fx_fingerprint.py \
  --candidate necko-fingerprint/comparison.json \
  --control necko-fingerprint/firefox-self.json \
  --out necko-fingerprint/fx-audit.json
```

`--enforce` делает устойчивые различия ошибкой (exit 1). На данном этапе CI
публикует отчёт без `--enforce`: ранее зафиксированные несовпадения H2
могут потребовать осознанного исправления до включения строгого gate.
Контроль Firefox самого с собой может показывать как случайный порядок
расширений, так и другие вариации. Их статус — **inconclusive**, не pass.
Тесты не измеряют обычную навигацию неизменённого Firefox, IP/TCP сигнатуры,
эффекты мобильной сети и эффективность против ТСПУ.

## 2. Память / горячий путь Necko

Ранее `AsyncIO.read()` создавал новый `Uint8Array` на каждый чтение
пакета (не более 32 КиБ). Теперь два независимых `pumpBuffered` создают
по одному 32-КиБ scratch-буферу на активное направление и используют его
до EOF или ошибки. Следующее чтение начинается **после** завершения
записи предыдущего чанка, поэтому данные не перезаписываются. При окончании
передачи буфер освобождается вместе с async pump. SOCKS setup по-прежнему
использует отдельные маленькие буферы.

Это снижение количества аллокаций на горячем пути, а не обещание снижения
пикового RSS или CPU: основная память Necko/Gecko остаётся нативной.
Проверка регрессий включает бинарные данные, backpressure, half-close,
ошибку записи и штатные native H2/H3 тесты.

## Проверка

```sh
node --test experiments/firefox-necko/client_test.cjs
python3 -m unittest discover -s scripts -p 'test_evaluate_fx_fingerprint.py' -v
# На Linux amd64 с тем же закреплённым libxul:
FOXTUNNEL_XPCSHELL=/path/to/runtime/xpcshell \
  go test -race ./experiments/firefox-necko -run '^TestGecko' -v
```

Workflow `necko-runtime-test.yml` теперь запускается при push в `fx`
и сохраняет `fx-audit.json` рядом с исходными wire-измерениями.
До получения новых native результатов нельзя количественно утверждать,
что FoxTunnel стал быстрее, экономнее или менее отличимым от Firefox.

## FX: последующие измерения и оптимизация вывода

В нативном JS-контуре функция `writeAllWithBackpressure` преобразует каждый
бинарный сегмент не более 32 КиБ в строку один раз и повторно использует
этот сегмент при коротких записях и `WOULD_BLOCK`. Это устраняет повторную
кодировку всего сегмента при каждом частичном `nsIOutputStream.write`;
сохраняются порядок байтов и backpressure. Диагностический снимок
`sessionStatus` обходится без временных массивов на каждую сессию.

Сравнитель fingerprint теперь сохраняет частоты расхождений для каждого
наблюдаемого поля и помечает `persistent_under_variable_control`, если
FoxTunnel расходится в каждом повторе, даже когда контроль Firefox сам по
себе вариативен. Этот статус означает **проверить**, а не «доказано
отличие». Поля HPACK и TLS по-прежнему не подгоняются вручную.

После пятиминутного CI-теста формируется
`necko-operations/fx-resource-report.json` с MiB/s прикладной передачи,
CPU seconds/GiB, RSS и GC. Исторические измерения включаются только
для справки: это разные запуски CI, поэтому численное преимущество
не утверждается до парных испытаний в одном окружении.

```sh
python3 scripts/report_fx_operations.py --current necko-operations \
  --reference experiments/firefox-necko/validation/stage4/ci-300s \
  --out necko-operations/fx-resource-report.json
```


## Третий коммит: исправление CI и кэша XPCOM

Исправлено повреждение YAML, из-за которого полный runtime workflow не
стартовал после второго коммита. Рабочий файл восстановлен от `main`,
и FX-проверки добавлены без изменения остальных gate. Исправлен сценарий
тестового Firefox-vs-Firefox контроля: два прогона без различий, один
с вариативным порядком расширений. Нативный `nsIBinaryInputStream`
создаётся один раз на каждый `AsyncIO`, а не на каждый read callback;
это оптимизация количества XPCOM wrapper allocations. Нативный CI должен
подтвердить корректность при H2 и H3; результат ещё не измеряет выигрыш.

## Финальные регрессионные испытания FX

* У `evaluate_fx_fingerprint.py` включён `--enforce` в нативном CI.
  Он блокирует новые устойчивые несовпадения измеренных полей. Отличия,
  которые возникают и между независимыми запусками Firefox, остаются
  *inconclusive* и отдельно отображаются с частотами.
* Нагрузочный тест сравнивает пред-FX `validation/baseline/client.js`
  (точный вариант из коммита `9a4261a`) с новым встроенным
  адаптером. Оба используют один и тот же уже проверенный libxul и по
  60 секунд на H2 и H3, один CI runner, одинаковую конфигурацию.
  Отчёт `necko-operations/paired-fx-report.json` проверяет CI-run ID
  и runner перед сравнением. Отдельный штатный 300-секундный тест
  сохраняется для проверки стабильности.
* Результат A/B — диагностическая точка. Для доказательства ускорения
  требуются повторные, чередующиеся замеры и контроль шумов ОС и раннера;
  порог на «ускорение» сейчас не используется. Не исключены различия
  в уровне загрузки runner между последовательными запусками.
* Тестовый базовый JS **никогда** не доступен через пользовательские настройки.
  Продакшен-движок всегда использует встроенный актуальный `clientScript`.

## Проверка случайных H2-расхождений

В реальном запуске 24 октября из трёх сравнений H2 лишь одно выявило
расхождение в `connection_1.h2_frames` (SETTINGS ACK перед/после
HEADERS) и `connection_1.hpack_blocks` (HPACK-длина). Три Firefox
self-controls не показали отличий в этих полях; этого недостаточно, чтобы
считать единичный случай постоянной регрессией. Алгоритм теперь:

- сохраняет `sporadic_fields` и полные частоты отклонений;
- помечает разовый случай как `inconclusive`, не как `equal`;
- блокирует `--enforce`, если несвойственное контролю отклонение
  появляется как минимум в двух третях повторений (и не меньше двух);
- отдельно сохраняет случайную вариативность из Firefox-vs-Firefox.

Ни равенство обычной навигации Firefox, ни устойчивость к ТСПУ эти
замеры не доказывают.

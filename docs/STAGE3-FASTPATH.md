# Этап 3/8 — TCP Fast Path: буферы и проверяемые оптимизации

**Ветка:** up. **Статус:** первая реализация (буферы копирования); остальные
изменения Fast Path требуют профилирования и проверки результата.

## Что изменено

1. `internal/tunnel/fastcopy.go`: общая повторно используемая scratch-память
   32 KiB для обходного пути стандартного `io.Copy`. Избегаем получения
   буфера из `sync.Pool`, если доступны `io.WriterTo` или `io.ReaderFrom`.
   В конце операции buffer очищается, чтобы текст пользователей не оставался
   в общем пуле.
2. Заменены `io.Copy` в обеих горутинах клиентского `streamConn` и в двух
   направлениях server CONNECT. Ошибки, graceful EOF, CloseWrite и политика
   отмены остаются на прежнем уровне.
3. Две отдельные `net.Pipe` в `streamConn` пока сохраняются намеренно:
   объединение в одну двунаправленную pipe ломает независимый half-close.
   Более агрессивный zero-copy требует новой реализации deadlines и тестов.
4. Юнит-, fuzz-, race-тесты и микробенчмарки сравнивают **одинаковый поток**
   через stdlib `io.Copy` и `fastCopy`; отдельный CI не блокирует сборку
   на основании шумных величин производительности GitHub runner.

## Команды

~~~sh
go test -race ./internal/tunnel -run '^(TestFastCopy|TestStreamOutlivesSetupTimeoutAndHalfClose|TestParallelStreams)' -count=1
go test ./internal/tunnel -run '^$' -fuzz '^FuzzFastCopy$' -fuzztime=2000x
go test ./internal/tunnel -run '^$' -bench '^BenchmarkFastCopyBaselineVsPool$' -benchmem -benchtime=200ms -count=5
~~~

Сравнивайте ns/op, B/op, allocs/op и B/s **только при одинаковом железе,
Go toolchain, типе transport и параметрах**. Подтверждённое повышение скорости
и снижение CPU на реальной сети отсутствует. Перед следующими оптимизациями
нужно снять профили heap/CPU и block на TCP bulk/small с теми же параметрами,
что используются в `docs/STAGE1-VLESS.md`.

## Воспроизводимые профили H2/H3 и NSS (шаг 2)

Теперь есть отдельный офлайн-профилировщик `scripts/stage3_profile.py`.
Он запускает реальные loopback SOCKS → FoxTunnel → локальный TCP echo
бенчмарки для **одного транспорта и одного размера** за запуск:

| Вариант CLI | Реальная трасса на loopback | Теги Go |
|---|---|---|
| `go-h2` | H2 CONNECT + Go TLS 1.3 | Без тегов |
| `go-h3` | H3 POST + quic-go | Без тегов |
| `nss-h2` | H2 CONNECT + Mozilla NSS TLS | `-tags nss`, Linux + CGO |

Сценарии `small` = 64 байта и `bulk` = 1 МиБ, повторяемые обмены
внутри уже открытого соединения. Это ближе к изолированному профилированию
быстрого пути, **не** полный CONNECT RTT. Для сценариев 1 КиБ/32 МиБ на
независимых VDS остаётся `docs/STAGE1-VLESS.md`.

Пример на Linux (внешняя приватная папка, не внутри Git):
~~~sh
python3 scripts/stage3_profile.py --variant go-h2 --scenario small \
  --benchtime 3s --out /tmp/ft-profiles/go-h2-small
python3 scripts/stage3_profile.py --variant go-h3 --scenario bulk \
  --benchtime 3s --out /tmp/ft-profiles/go-h3-bulk
python3 scripts/stage3_profile.py --variant nss-h2 --scenario bulk \
  --benchtime 3s --out /tmp/ft-profiles/nss-h2-bulk
~~~
Каталог `/tmp/ft-profiles` следует создать заранее с правами `0700`.
Каждый выходной каталог создаётся однократно, `0700`, без перезаписи.
Внутри: `cpu.pprof`, `mem.pprof`, `block.pprof`, `mutex.pprof`,
`go-test.log`, `summary.json`. Файлы с правами `0600` на Linux.

Анализ в локальной среде (не размещать сырые профили в сети):
~~~sh
go tool pprof -top /tmp/ft-profiles/go-h2-small/cpu.pprof
go tool pprof -top -alloc_space /tmp/ft-profiles/go-h3-bulk/mem.pprof
go tool pprof -top /tmp/ft-profiles/nss-h2-bulk/block.pprof
~~~

Для `nss-h2` нужен работающий CGO и dev-пакеты NSS/NSPR. Go CPU pprof
не учитывает потребление CPU **внутри нативного C NSS**, поэтому для
достоверной оценки NSS↔Go FFI необходим дополнительный нативный профайлер
и измерение полного процесса. CPU/heap/block/mutex Go-профили нельзя
интерпретировать как абсолютную стоимость C-библиотеки.

CI выполняет шесть парных профилей (3 варианта × 2 размера), но не загружает
сырые `.pprof` в артефакты. Метрики CI не являются повторяемым WAN
бенчмарком, а `pprof` могут содержать пути к файлам и другую служебную
информацию. Для анализа реальных регрессий сохраняйте приватные профили
и повторяйте по несколько запусков на одинаковом железе и коммите.

## Серверный TCP → HTTP response: управляемое копирование

Вызов `fastCopy(outgoing, upstream)` на сервере использовал необязательные
методы `WriterTo` / `ReaderFrom` объектов `net.Conn`. Для TCP → HTTP
`ResponseWriter` системные `sendfile/splice` неприменимы, поэтому при
fallback могут создаваться дополнительные временные буферы.

Теперь для **единственного** направления «destination TCP → HTTP-ответ»
используется `fastCopyHTTPResponse`. Он скрывает необязательные методы
копирования у источника/назначения и направляет данные через один
очищаемый scratch-буфер из существующего `sync.Pool`. Для остальных
направлений общий `fastCopy` по-прежнему сохраняет оптимальные
`WriterTo` / `ReaderFrom` пути.

Не изменены: обработка ошибок `Read/Write`, немедленный `Flush()`
интерактивных данных, версия padding, half-close, лимиты соединений,
отмена и закрытие HTTP-запроса. Нет задержки отправки пакетов из-за
накопления данных. Сохраняются две `net.Pipe` и две client pump goroutines:
прямой доступ к телу HTTP-ответа потребовал бы корректной реализации
`SetReadDeadline` и сохранения независимого `CloseWrite`.

Новые тесты запрещают обход буфера путём вызова `WriterTo`/ `ReaderFrom`
на указанном направлении и проверяют передачу, ошибки и `Flush`.
`BenchmarkFastCopyHTTPResponse` сравнивает семантику копирования с
`bytes.Reader`, поэтому **не является замером выгоды на TCPConn**.
Эффект по CPU и throughput должен быть подтверждён повторами
транспортных бенчмарков (`go-h2`, `go-h3`, `nss-h2`) на одинаковом
сервере; на GitHub runner нельзя делать выводы из несопоставимых
разрозненных запусков.

### Сравнение на настоящем TCPConn (локальный GitHub runner)

В CI `Stage 3 TCP Fast Path` run `39421694134` используется настоящий
`net.TCPConn` как источник и сбрасывающий данные `ResponseWriter` с
`Flush()`. В отличие от синтетического `bytes.Reader` этот тест
действительно вызывает `TCPConn.WriteTo` в базовой версии.

| Один локальный прогон | `fastCopy` / TCPConn.WriteTo | `fastCopyHTTPResponse` |
|---|---:|---:|
| 64 Б, ns/op | 50 893 | 48 572 |
| 64 Б, B/op | 32 846 | 141 |
| 1 МиБ, ns/op | 490 796 | 462 685 |
| 1 МиБ, B/op | 32 848 | 114 |

Это **не** замер пропускной способности сети VPN: нет TLS, HTTP/2
кадров, WAN и VLESS. Время может меняться из-за CPU планировщика и
GitHub runner. Аллокаций по количеству стало на одну **больше** на операцию,
но общий размер выделяемой памяти существенно ниже. При источнике
`bytes.Reader` старый `WriterTo` ожидаемо быстрее; новый путь поэтому
используется строго в серверном направлении TCP → HTTP response, а не
повсеместно. Для оценки производительности всего туннеля следует
повторять H2/H3/NSS профили на одинаковой машине.

## NSS ↔ Go FFI: исключение лишней синхронизации ошибок

Проверен фактический путь NSS 3.130/NSPR TLS через `internal/nsstls`.
Приложение передаёт полезные данные **без промежуточного `C.GoBytes`**:
NSS `PR_Read/PR_Write` вызывает C → Go callback, который обращается к
существующему сокету через `unsafe.Slice` с заимствованным C-буфером
только на время callback. `C.GoBytes` остаётся для сертификатов, где копия
нужна для безопасного Go x509 parsing и не относится к потоку данных.

Обнаружен лишний `sync.Mutex` в успешном callback `ft_go_read`: каждое
чтение захватывало один глобальный для read/write замок, чтобы сохранить
`readErr` даже когда ошибки не было. Он заменён **двумя независимыми
`atomic.Pointer[ioFailure]`** (`readFault`, `writeFault`).
На входе в `Read`/`Write` старое состояние ошибок очищается атомарно один
раз; успешный C→Go callback не выполняет синхронизацию; ошибка публикуется
отдельным неизменяемым объектом. Это важно для одновременного чтения,
записи и закрытия, а также предотвращает возврат устаревшей ошибки.
Ограничение NSS 3.130, проверка TLS, ALPN, управляемые Go net.Conn и
прежнее поведение half-close не изменены.

Набор `TestStage3NSSFaultState*` проверяет изоляцию ошибок и конкуренцию
между направлениями с `-race`. Дополнительно используются реальные NSS
SOCKS/H2 тесты, в том числе half-close, и две оценки:
- `BenchmarkStage3NSSFaultState`: только цена lock/unlock против atomics
  в Go; **не** измеряет стоимость вызова C→Go или криптографию NSS.
- `BenchmarkStage3NSSH2`: действительная TLS-передача по loopback
  через NSS/H2, без независимого WAN. Этот тест **не** сопоставим с
  предшествующим коммитом без повторения на одинаковом железе.

### Локальные бенчмарки и пределы оценки

Из [Stage 3 CI №39422970424](https://github.com/SawaMEN/FoxTunnel/actions/runs/39422970424),
один Linux GitHub runner, **до уточнения положения обнуления ошибок**:

| Только Go error bookkeeping | Mutex | Atomic |
|---|---:|---:|
| Успешная операция (нс) | 5,406 | 4,957 |
| Ошибка (нс) | 5,322 | 26,80 |
| Память на ошибку | 0 Б | 16 Б |

На обновлённом пути сброс ошибки производится **один раз на public Read/Write**,
поэтому таблица показывает лишь ориентир стоимости primitive, а не полный
результат TLS I/O. Редкая ветка ошибок теперь выделяет объект; при высокой
частоте отказов её нужно оценивать отдельно.

В этом же запуске `BenchmarkStage3NSSH2` измерял ~0,235 мс на 64 Б и
~5,50 мс на 1 МиБ. Это только loopback с настоящим TLS 1.3, без
сравнения до/после на одном хосте. Ускорение NSS или снижение полного CPU
протокола на VDS пока не доказано.

Нужен дальнейший `perf`/нативный профайлер для учёта полного CPU внутри NSS,
реального числа Cgo callback, размера TLS record, а затем повторная оценка
на VDS. Перенос NSS I/O в C или объединение callbacks не сделаны: это
изменение протокола управления сетевым сокетом потребует отдельного
дизайна отмены, сроков жизни и тестов.
 
## Необязательный эксперимент WAN/VDS: тройной baseline (не блокирует этап)

Добавлен [воспроизводимый runbook этапа 3](STAGE3-WAN.md), а также
scripts/stage3_wan.py и scripts/stage3_wan_gate.py. Один прогон измеряет
три SOCKS-цепочки с одинаковой полезной нагрузкой и чередуемым порядком:

- FoxTunnel до первых Fast Path изменений (commit
  23d3ba78dcf77fb810a26ef27b1a30133490ce86);
- FoxTunnel актуального полного commit из ветки up;
- независимый Xray/VLESS с зафиксированным режимом и версией.

Gate принимает **только** три совпадающих UTC-дня с парами сценариев
small 1 КиБ / bulk 32 МиБ и проверяет отсутствие значительной
регрессии в целостности, успешности, p95, медианной скорости, CPU/RSS.
Отчёты не содержат адресов, исходных ошибок SOCKS и PID.

**Необязательные полевые прогоны не выполнены и не требуются для этапа 3.** CI использует fake SOCKS и локальный
echo; независимость VDS или работа реальной версии Xray этим не доказаны.
Даже условный PASS трёхдневного gate означает только заданную
границу регрессии, но не ускорение протокола как таковое.

# Следующие этапы FoxTunnel

**Русский** | [English](NEXT-STEPS.en.md)

Оценка после main `bc257ef` от 18 октября 2026 года. Это инженерные приоритеты,
а не обещание устойчивости к ТСПУ. Уже есть семь встроенных транспортов, NSS TLS,
одна ссылка на кластер, ограниченные очереди и локальные проверки отказов.

| Приоритет | Что изменить | Как принять результат |
|---|---|---|
| 1: развёртывание XHTTP | Общий path/Host, безопасная нормализация, настройка/ссылка/присоединение | Три режима через управляемый HTTPS-фронтенд; разные Host/SNI; NSS; отказ неверных сертификатов до HTTP; кластер с пользовательским маршрутом |
| 2: эффективность | Объединение мелких записей и ограниченный конвейер packet-up; затем постоянные bond-каналы | Один и тот же benchmark с RTT/потерями; CPU/allocations/память; порядок и отсутствие replay при потере ACK; медленная нода не заполняет неограниченную очередь |
| 3: Mozilla | Эталонные записи конкретной версии Firefox и ОС; сравнение полного TLS/H2; эксперимент клиентского Neqo | Воспроизводимые снимки TLS/H2/QUIC, версии NSS и браузера; проверяемый список различий; отдельная сборка/тест Neqo, без заявления совпадения по одному NSS |
| 4: управление доступом и VPN | Раздельные пользователи и отзыв, UDP, TUN, маршрутизация/DNS/kill switch | Отзыв одного пользователя не отключает остальных; ограничения UDP; тесты отсутствия прямого обхода маршрута и утечек DNS при отказе |
| 5: эксплуатация | Полезная скорость/занятость нод, диагностика, корректная остановка, полевые испытания | Согласованные обезличенные измерения у операторов РФ; успешность/восстановление/RTT/скорость/CPU/ОЗУ; отрицательные результаты публикуются рядом с положительными |

На этом этапе выполнен приоритет 1: настройки маршрута и авторизации проходят
через весь процесс, новый setup генерирует независимый случайный путь, join
наследует его. Это не полная совместимость с эталонным XHTTP: ещё нужны независимые
wire-тесты, XMUX и отдельные адреса направлений. HTTP-фронтенд в тестах настроен
явно; произвольный CDN не проверен.

Окно XHTTP packet-up теперь ограничено четырьмя запросами: тела пишутся по порядку,
ACK освобождают только непрерывную подтверждённую последовательность, повторной
отправки при неоднозначном ответе нет. На стенде с задержкой ACK 40 мс: 0,80 →
3,18 МБ/с (256 КиБ carrier echo, Go TLS). Полный локальный SOCKS/inner-H2 echo:
38,44–42,78 → 95,84–96,13 МБ/с; выделенные байты на 1 МиБ снизились с 5,16–5,33
до 3,69–3,87 МБ, число аллокаций выросло примерно с 17,4 тыс. до 19,8–20,0 тыс.
Это короткие локальные замеры, не Интернет и не производительность NSS.

[Сняты живые TLS/H2-профили Firefox 158 и FoxTunnel](WEB-PROFILE.md), включая NSS
3.98 и ту же NSS 3.130 из Firefox. Зафиксированы различия Hello, SETTINGS и окон.
Следующий этап Mozilla — реальное поведение стека, затем одинаковые сценарии
трафика и полевые тесты операторов. Обход ТСПУ этими измерениями не установлен.

Незавершённый ECH-черновик остаётся отдельно: он использует Go TLS, не NSS.
Перед включением нужны проверки отказа без downgrade/credentials, ротации ключей,
SNI/pin и кэшей, setup/кластера. Сам по себе он не продвигает Firefox-совместимость.

[Mozilla Neqo](https://github.com/mozilla/neqo) реализует QUIC/H3/QPACK и использует
NSS. Его README отдельно запрещает production-применение экспериментального
сервера. Поэтому сначала рассматривается клиентская интеграция с нашим сервером,
а не замена сервера на Neqo. [Описание XHTTP](https://github.com/XTLS/Xray-core/discussions/4113)
служит источником для тестов транспорта, не гарантией работы FoxTunnel у операторов.

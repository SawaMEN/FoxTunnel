# Встроенные транспорты без Xray

**Русский** | [English](NATIVE-TRANSPORTS.en.md)

FoxTunnel сам принимает и создаёт шесть вариантов соединения. Xray, sing-box,
внешний SOCKS-транспорт и отдельный клиент другого протокола не требуются.
WebSocket и QUIC реализованы зависимостями Go, включаемыми в один бинарный файл.

| `transport` | На внешнем соединении | TLS клиента | Объединение нод и discovery |
|---|---|---|---|
| `h2-connect` | TLS 1.3, HTTP/2 CONNECT | Go или экспериментальный NSS | Да |
| `h2-post` | TLS 1.3, двусторонний POST по HTTP/2 | Go или экспериментальный NSS | Да |
| `wss` | TLS 1.3, HTTP/1.1 WebSocket; внутри мультиплексированный HTTP/2 | Go или экспериментальный NSS | Да |
| `h3-post` | HTTP/3 POST поверх QUIC/UDP с TLS 1.3 | Go QUIC TLS | Да |
| `xhttp-stream-one` | Двусторонний POST; внутри HTTP/2 FoxTunnel | Go или экспериментальный NSS | Да |
| `xhttp-stream-up` | Раздельные потоковые POST/GET с UUID сессии; внутри HTTP/2 FoxTunnel | Go или экспериментальный NSS | Да |

Во всех режимах есть проверка CA/имени, дополнительный SPKI pin, одинаковая
авторизация, ограничения назначений, полузакрытие отправки и отмена потоков.
В WSS один внешний WebSocket переносит несколько HTTP/2-потоков; второго слоя
TLS внутри него нет. Ограничение — 32 одновременных внутренних потока на
соединение, сообщения до 64 КиБ, исходящие сообщения до 32 КиБ; сжатие выключено.
Сервер дополнительно ограничивает число внешних WSS-соединений через `max-tunnels`.

H3 использует обычный QUIC, без Salamander/Gecko и без воспроизведения Firefox.
Новый клиент завершает TLS до отправки HTTP; 0-RTT выключен. Ограничены потоки,
окна приёма и заголовки; `max-connections` отдельно ограничивает QUIC-соединения,
включая незавершённые рукопожатия. При достижении половины лимита включается
проверка адреса через QUIC Retry. Лимит независим от TCP-слушателя.
H3 переносит TCP-трафик приложений: это ещё не UDP ASSOCIATE или TUN.

## Автоматическая подготовка

Например, встроенный WSS с Mozilla NSS на клиенте:

```sh
./foxtunnel setup --server https://main.example \
  --cert /etc/certs/main/fullchain.pem --key /etc/certs/main/key.pem \
  --transport wss --tls-backend nss --out main-node
./foxtunnel server --config main-node/server.json
./foxtunnel client --link-file main-node/connection.txt
```

Клиент для этого примера собирается с `-tags nss` и требует NSS/NSPR. Обычный
Go-бинарный файл поддерживает WSS с `--tls-backend go`. Серверу NSS не нужен.
Внешний ALPN WSS — `http/1.1`, у прямых H2-режимов — `h2`.

Для QUIC замените параметры на `--transport h3-post --tls-backend go`.
`setup` запишет `"h3_listen": ":443"` в серверный JSON. Для H2/WSS достаточно
TCP 443; для H3 необходимо также разрешить UDP 443 на сервере и в сети.
Регистрация входов выполняется обычным `cluster-add`. При присоединении по
`--join-link-file` сохраняется транспорт главного профиля, для H3 также
включается UDP-слушатель входа. Связь входа с общим выходом пока остаётся H2/TLS;
между ними должна быть доступна TCP-связь. У всех опубликованных входов должен
быть доступен выбранный клиентом транспорт.

Для ручного запуска серверного UDP-слушателя используйте `server --h3-listen :443`
вместе с обычными `--cert`, `--key` и адресом TCP. Действующие сертификаты,
DNS и правила firewall остаются обязанностью администратора.

## Ссылки и настройки

`client --transport h2-post`, `client --transport wss` и `client --transport h3-post`
работают с ручными параметрами подключения. `share --transport …` экспортирует
поле `transport` в `vetroff://`. При импорте ссылки используется её режим;
смешивание с флагами подключения отклоняется. Старые ссылки без поля используют
`h2-connect`; старые клиенты отклоняют ссылки с новым неизвестным полем.
SNI и pin координатора и каждого входа сохраняют прежнюю область действия.

Режим выбирается явно. Отказ сертификата, pin, авторизации или согласования
не вызывает переход на другой протокол. Резервирование между доверенными
нодами продолжает работать в рамках выбранного транспорта. Автоматического
перебора всех маскировок и выбора транспорта по измеренной скорости пока нет.

## Связки и XHTTP

Уже доступны встроенные связки `FoxTunnel → H2 POST → TLS`,
`FoxTunnel → HTTP/2 → WebSocket → TLS` и `FoxTunnel → H3 POST → QUIC`.
Они используют собственную авторизацию и формат FoxTunnel. `h2-post` и
`h3-post` — потоковая передача через POST; это **не совместимость с Xray XHTTP**.

Добавлены независимые потоковые carriers `xhttp-stream-one` и `xhttp-stream-up`.
Они следуют базовой форме запросов XHTTP; внутри остаётся FoxTunnel, а не VLESS.
Работают с Mozilla NSS, `setup`, `vetroff://`, discovery и объединением нод.
`packet-up`, XMUX, пользовательский path/Host и тесты совместимости с Xray пока
не реализованы. Это не заявление о полной совместимости XHTTP. Подробнее:
[XHTTP и Mozilla NSS](XHTTP.md).
Отдельный исполняемый Xray для такой будущей реализации не обязателен.

Сейчас нет нативных REALITY, ECH, gRPC, HTTPUpgrade, DNS-туннеля dnstt,
Salamander/Gecko, AWG или произвольного объединения этих форматов. Их анализ
не означает наличие реализации. ECH требует согласованных ключей и поддержки
сервера; QUIC-обфускация перестаёт выглядеть обычным HTTP/3. Случайное смешивание
форматов и подмена одного только SNI не обеспечивают маскировку браузера.

## Что подтверждено для РФ

На этом этапе подтверждена локальная работоспособность, а не проходимость ТСПУ.
Для всех новых транспортов проверены крупные передачи, полузакрытие, отмена,
запрет неверных CA/SNI/pin до отправки HTTP, discovery и два входа с потерей ACK,
дедупликацией и отказом пути. Для WSS/H2 POST есть отдельные проверки NSS.
Это не доказывает одинаковую доступность у российских операторов.

Практические ограничения для испытаний:

- При фильтрации UDP H3 будет недоступен; H2 и WSS остаются TCP-вариантами.
- WSS может проходить через фронтенд с поддержкой WebSocket. Необходимо проверить
  сохранение авторизации, таймауты и лимиты конкретного фронтенда; совместимость
  с произвольным CDN не заявляется.
- Двусторонний POST требует немедленной передачи запросов и ответов. Буферизация
  у обратного прокси может остановить интерактивный поток.
- TLS скрывает HTTP-заголовки от промежуточной сети, но не IP, размеры, время
  и открытый SNI. TLS-терминатор видит HTTP и доверяется как входная нода.
- Встроенный NSS не равен полному Firefox; HTTP-поведение Go и профиль QUIC
  требуют отдельных измерений. Дополнение первых записей не делает их браузерными.

Нужны испытания на фиксированных версиях в нескольких сетях РФ: успешность
подключения, p50/p95 установки, полезные Мбит/с, потери/восстановление,
CPU/ОЗУ и наблюдаемый профиль. Без таких данных нет оснований выбирать режим
как «самый быстрый» или «необнаружимый».

## Локальное сравнение скорости

Один существующий SOCKS-поток, передача/эхо блоками 1 МиБ, Go TLS, без padding,
без bond, Linux amd64 / AMD EPYC 9V74, Go 1.26.9. Два коротких прогона по 300 мс,
`go test ./internal/tunnel -run '^$' -bench 'BenchmarkNativeTransports/.*/1MiB' -benchtime=300ms -count=2`.

| Режим | Полезная скорость, МБ/с | Выделения на 1 МиБ |
|---|---:|---:|
| H2 CONNECT | 266–334 | 641–662 |
| H2 POST | 315–331 | 636–646 |
| WSS | 145–165 | 4313–4656 |
| H3 POST | 184–196 | 9002–9026 |

Это шумные короткие loopback-измерения, не интернет, не Мбит/с и не доказательство
превосходства. Полезные байты считаются один раз при полном echo round trip.
WSS и QUIC увеличивают работу с кадрами/пакетами. Под потерями и задержкой
соотношение может измениться; для выбора в РФ нужны реальные измерения.

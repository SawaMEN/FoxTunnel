Команды:

```sh
./foxtunnel check-config --config server-config/server.json
./foxtunnel check-config --link-file connection.txt --json
./foxtunnel check-config --link-file connection.txt --ca-cert local-ca.pem --engine mozilla
```

Укажите ровно один файл. Клиентский профиль должен быть приватным обычным
файлом; stdin не поддерживается. `--engine` и `--ca-cert` применяются только
к клиенту. Пути внутри server.json сохраняют семантику запуска сервера:
относительные пути разрешаются от текущего рабочего каталога.

Команда читает конфигурацию и локальные зависимости, создаёт и закрывает
объекты транспорта, но не выполняет DNS-запросов, не подключается к серверам,
не занимает порты и не записывает конфигурацию или журнал квот.
Discovery проверяется только как локальная настройка профиля.
`doctor` проверяет выбранную proxy-ноду; полный discovery/bond-граф он не проверяет.

Серверная проверка включает формат JSON, ограничения, сочетания параметров,
синтаксис listen с числовым портом, соответствие и срок сертификата/ключа,
файлы пользователей/существующий журнал квот, кластер, public web root и
локальную настройку relay. В клиентской проверке применяются существующие
валидаторы профиля и транспорта, включая наличие NSS/Neqo в текущей сборке.

PASS означает успешную локальную проверку перечисленных условий. Он не
подтверждает доверие удалённого клиента к сертификату, доступность порта,
права на будущую запись, доступность блокировки журнала или авторизацию на
сервере. Отсутствующий журнал квот разрешён; проверка не создаёт его и не
получает блокировку работающего сервера. Настройки могут измениться после
проверки — запуск сервера по-прежнему выполняет собственную валидацию.

JSON schema 1 содержит `role`, `ok`, массив `checks` (`code`, `ok`, `message`)
и при успехе `settings`. Выводятся только разрешённые параметры: режимы,
лимиты, число серверов и флаги. Адреса, имена пользователей, пароли, пути,
SNI, pins, URL и содержимое ошибок парсера не выводятся.
`tls_backend` описывает политику выбора (`auto`, `go`, `nss`), а не результат
удалённого handshake. Код завершения: 0 при успехе, ненулевой при ошибке.
Ошибки аргументов выводятся на stderr; отчёт JSON доступен после корректного
выбора входного файла. Тексты сообщений английские и не являются кодами API.

```sh
./foxtunnel doctor --link-file connection.txt --target echo.example.com:9000
./foxtunnel doctor --link-file connection.txt --target echo.example.com:9001 --network udp --json
./foxtunnel doctor --link-file connection.txt --target echo.example.com:9000 --server-index 1 --timeout 10s
```

`--target` обязателен: это доступный с сервера **echo-сервис под вашим
управлением**, возвращающий полученные байты без изменения. Команда отправляет
32 случайных байта; обычный HTTP/HTTPS-сайт для этой проверки не подходит.
TCP и UDP echo-сервисы могут иметь разные порты. Сервис должен быть разрешён
политикой выхода сервера. Приватные назначения по умолчанию ограничены;
команда не меняет эту политику. Для изолированных стендов в репозитории есть
`scripts/echo_server.py` и `scripts/udp_echo_server.py`.

Проверки выполняются последовательно до первой ошибки:

1. Приватный профиль и локальная конфигурация backend/CA.
2. Локальный DNS имени выбранного proxy; IP-адрес не требует DNS-запроса.
3. HEAD через выбранный транспорт с обычной проверкой CA, hostname/SNI и pin.
4. Для TCP — открытие настоящего туннеля и обмен с echo-сервисом.
   Для UDP — один запрос/ответ UDP-v1 через выбранный HTTPS-транспорт.

Имя `--target` разрешает удалённый exit, а не локальная DNS-проверка. DNS proxy
проверяется отдельно; последующее соединение использует обычный resolver
транспорта и может получить другой адрес. Это диагностика разрешения имени,
а не закрепление IP или обещание проверить все A/AAAA-адреса.

По умолчанию проверяется первая нода. `--server-index` — индекс от 0 до 7,
который должен существовать в профиле. Проверяется только выбранная нода:
балансировка, bonding, discovery и другие fallback-ноды не используются.
Основные SNI/pin профиля относятся только к ноде 0; остальные сохраняют
обычную проверку CA/hostname. Отдельный файл per-node pins команда пока не
принимает. Для проверки такой политики используйте отдельный профиль с
нужной нодой в качестве основной и её собственным pin.

`--engine mozilla` выбирает NSS/Neqo по обычным правилам доступности сборки.
H3→H2 fallback намеренно отключён: успешный H2 не доказывает доступность QUIC.
Транспорт из профиля не заменяется автоматически. HEAD не следует redirect,
не открывает тестовое назначение и не добавляет inner Proxy-Authorization;
внешние WSS/XHTTP сохраняют штатную авторизацию после проверки TLS.
У WSS/XHTTP номер HTTP в отчёте относится к внутреннему соединению.

Общий таймаут сетевых проверок — 15 секунд; `--timeout` принимает 100ms–2m.
Более короткие штатные таймауты ядра также действуют, включая UDP-v1.
Отмена останавливает запрос и закрывает созданное TCP-соединение.
После передачи payload команда не делает повторных попыток. Файл профиля
не изменяется, локальный SOCKS-слушатель не запускается.

Успешный HEAD подтверждает защищённый carrier, но не авторизацию: обычный
ответ сайта, включая 302/404, может быть нормальным результатом HEAD.
Авторизованный туннель и payload проверяются следующими шагами. При отказе
сервер может скрывать причину ответом сайта, поэтому `tunnel_rejected` не
означает однозначно неверный пароль. Успех echo подтверждает этот обмен,
а не скорость, отсутствие фильтрации или строгость серверной политики доступа.

JSON schema 1 содержит `ok`, `network`, `server_index`, `transport`, `engine`,
`duration_ms` и `checks`. Каждый шаг имеет `stage`, `ok`, `reason`,
`duration_ms`; у ответа транспорта также есть `http_major` и `http_status`.
Адреса, цели, paths, учётные данные, pins, payload, заголовки, тела ответов и
произвольные тексты ошибок в отчёт не попадают. Пропущенные после отказа шаги
не добавляются. Код завершения 0 означает успех всех выполненных проверок;
при отказе он ненулевой. Ошибки аргументов идут на stderr без JSON-отчёта.

Основные причины отказа:

| reason | Что проверять |
|---|---|
| `invalid_profile_or_local_files` | Профиль, выбранный индекс и наличие CA-файла |
| `engine_or_trust_configuration_failed` | Наличие backend и локальные настройки доверия |
| `proxy_dns_failed` | Разрешение имени proxy на стороне клиента |
| `tls_trust_failed` | CA, срок сертификата, hostname/SNI и pin |
| `protocol_negotiation_failed` | HTTP 426 либо отсутствующее/несовместимое подтверждение версии или capabilities |
| `tls_or_carrier_failed` | Соединение и совместимость выбранного carrier |
| `authentication_or_policy_rejected` | Явный HTTP-отказ 401/403/407; причина может быть политикой |
| `server_limited_or_unavailable` | Ответ 429/503, лимиты или доступность сервера |
| `destination_or_policy_unavailable` | Ответ 502/504, назначение или политика выхода |
| `tunnel_rejected`, `tunnel_setup_failed` | Отказ открытия туннеля; пароль не является единственной возможной причиной |
| `tcp_exchange_failed`, `udp_exchange_failed` | Передача данных и доступность echo-сервиса |
| `echo_mismatch` | Сервис вернул другие байты |
| `timeout`, `canceled` | Истёк бюджет времени или проверка отменена |

UDP-режим требует включённого UDP на сервере. Он проверяет один небольшой
UDP-v1 обмен и не подтверждает streaming-v2, NAT migration, Internet MTU,
длительную работу, игры или звонки. UDP echo поверх H2 не доказывает
доступность внешнего UDP/QUIC: для этого профиль должен выбирать H3.

Старый peer в новых CLI-тестах моделируется HTTP/2 endpoint без подтверждения;
это не новая сертификация всех исторических бинарников. Эти локальные результаты

[NSS CI](https://github.com/SawaMEN/FoxTunnel/actions/runs/39672481479).

`TestNativeBondedLanesGo/xhttp-packet-up` (`destination redialed`). Повторный
успех не означает устранения причины этой нестабильности.

Политика `legacy` сохраняет прежнюю совместимость. `strict` требует точного
подтверждения текущего wire draft и необходимых возможностей TCP/UDP в ответе
сервера. Это проверка совместимости, а не выбор шифрования или fingerprint.
TLS и авторизация по-прежнему проверяются независимо.

Для новой прямой конфигурации:

```sh
./foxtunnel setup --server https://vpn.example.com \
  --cert /path/to/fullchain.pem --key /path/to/privkey.pem \
  --protocol-policy strict --out strict-config
./foxtunnel check-config --config strict-config/server.json
./foxtunnel server --config strict-config/server.json
./foxtunnel client --link-file strict-config/connection.txt
./foxtunnel doctor --link-file strict-config/connection.txt --target echo.example.com:9000 --json
```

Для частного CA добавьте `--ca-cert` при setup и запуске/диагностике клиента.
`setup --protocol-policy strict` сохраняет политику на обеих сторонах, создаёт
прямой профиль без bonding/discovery и не создаёт cluster.json. `node.json`
с публичной идентичностью по-прежнему входит в набор. Присоединение relay
через `--join-link-file` в strict запрещено.

При ручном запуске без файлов добавьте `--protocol-policy strict` к `server`
и `client`. Для экспорта прямого профиля существующего сервера используйте
`share --server https://vpn.example.com --protocol-policy strict --out connection.txt`;
учётные данные берутся из штатных переменных окружения. Команда share не
изменяет сервер: его политику нужно настроить отдельно.

В существующем серверном JSON поле `"protocol_policy": "strict"` включает
требование согласования после перезапуска. В клиентском профиле применяется
то же поле, которое сохраняют setup/share. Сначала обновите бинарники сервера
и клиента; новый клиент strict работает с обновлённым сервером в legacy,
так как тот подтверждает совместимый offer. После проверки можно перевести
сервер в strict. Старые клиенты после этого будут получать отказ 426.

Профиль владеет своими настройками: `client`/`share --link-file` нельзя
совмещать с `--protocol-policy`, даже для переключения в legacy. Аналогично
нельзя смешивать `server --config` с этим флагом. Для явного возврата в legacy
измените серверный JSON и создайте отдельный legacy-профиль, затем перезапустите
процессы. При ошибке согласования приложение само политику не понижает.

| Клиент | Сервер | Результат |
|---|---|---|
| Старый профиль без поля | Обновлённый legacy | Прежняя работа без гарантии согласования |
| Legacy | Strict | Отказ 426 до открытия назначения |
| Strict | Обновлённый legacy или strict | Требуется текущая версия и необходимые capabilities |
| Strict | Старый сервер без подтверждения | Отказ без повторной попытки в legacy |
| Старый бинарник | Новый strict-профиль | Ошибка неизвестного поля при чтении профиля |

В JSON разрешены только строки `legacy` и `strict`. Отсутствующее поле
означает legacy; `null`, пустая строка, опечатки, иной тип, повторяющиеся
ключи и их регистровые варианты отклоняются. Legacy-экспорт пропускает поле
для совместимости старых читателей. `check-config` показывает эффективную
политику в settings, `doctor` — в `protocol_policy`; это запрошенная политика,
а не подтверждение удалённого сервера до открытия TCP/UDP-маршрута.

Согласование действует для TCP, UDP-v1 и UDP-stream-v2, включая внутренний
H2 WSS/XHTTP. Bond/cluster RPC не согласуются: strict не разрешается с
bond/discovery ни в профиле, ни в CLI/серверном JSON. Гарантии протокола для
этих расширений требуют отдельной реализации.

TCP и UDP-stream-v2 не отправляют данные приложения до подтверждения.
**UDP-v1 содержит датаграмму уже в запросе:** старый сервер может обработать
её до того, как strict-клиент отклонит ответ без подтверждения. Для гарантии
проверки до payload используйте известный strict-сервер или UDP-stream-v2.
`doctor --network udp` проверяет UDP-v1 и сохраняет это ограничение.

Подробный контракт: [wire negotiation](reference/WIRE-NEGOTIATION.md).

`Status().operations`, `Snapshot().Transport.Operations` и transport snapshot
в `WatchStatus` содержат одни и те же локальные агрегаты. CLI выводит их через
существующий `--engine-status-interval`. Schema остаётся 1: поля добавлены,
прежние поля сохраняются; JSON-читатель должен разрешать неизвестные поля.

| Раздел JSON `operations` | Что измеряется |
|---|---|
| `tcp_setup` | Один логический CONNECT setup, включая попытки fallback до окончательного результата |
| `udp_exchange` | Один UDP-v1 HTTPS запрос/ответ и разбор frame; 204 учитывается как `udp_no_response` |
| `udp_stream_setup` | Открытие одного carrier UDP-stream-v2, включая carriers многонодового режима |
| `rejections.sdk_capacity` | Отказы общего SDK-лимита TCP/UDP и принятых SDK SOCKS-соединений |
| `rejections.socks_capacity` | Отказы лимита SOCKS runtime |
| `rejections.udp_pending_capacity` | Отброшенные SOCKS UDP запросы при занятых восьми слотах ассоциации |
| `rejections.udp_receive_queue_drops` | Ответы, отброшенные заполненной входящей очередью UDPConn |
| `recovery` | Первый успешный новый вызов после последнего отказа или уведомления о смене сети |

Каждая операция содержит `started`, `succeeded`, `failed`, `active`,
`last_duration_us`, `total_duration_us`, `max_duration_us`, `last_reason`
и фиксированные счётчики `failures`. Длительности — целые микросекунды по
монотонным часам; `active` означает незавершённые измеряемые вызовы,
а не число установленных потоков. Последний результат зависит от порядка
завершения конкурентных вызовов. Среднее можно получить как
`total_duration_us / (succeeded + failed)` при ненулевом знаменателе.

Причины: `ok`, `canceled`, `timeout`, `tls_trust_failed`,
`protocol_negotiation_failed`, `peer_rejected`, `peer_limited_or_unavailable`,
`network_failed`, `transport_capacity`, `udp_no_response`, `other_failure`.
Классификация использует типы ошибок и HTTP status, без разбора текста.
HTTP 426 относится к протоколу, 429/503 — к лимитам/доступности peer;
прочие отказы HTTP не доказывают неверный пароль. Причины выбора H3/H2
ограничены `direct`, `cooldown`, `unreachable`, `probe`, `network-change`;
неизвестные значения заменяются на `unknown`. Старые route counters показывают
выбор транспорта, а не успешный setup. Это не учёт всех межнодовых fallback.

`after_failure` и `after_network_change` увеличиваются один раз при первом
успешном вызове, начатом после соответствующего последнего события;
`last_failure_recovery_us` и `last_network_recovery_us` измеряют время от него.
Уже выполнявшийся вызов не подтверждает более позднее событие. Повторные
события сдвигают начало отсчёта к последнему. Отмена и локальный capacity
учитываются как отказы операций, но не начинают период восстановления.
Агрегат общий для клиента: успех может относиться к другому назначению/ноде.
Он не доказывает восстановление старого потока или всей внешней сети.

Не измеряются локальная валидация до сетевого вызова, отключённый UDP,
Bond setup, HEAD/probes и ошибки передачи уже открытых потоков. Проверка
совпадения адреса UDP-ответа во внешнем wrapper выполняется после измерения;
успех UDP-v1 здесь означает успешный ответ/frame, а не полную проверку
прикладного протокола. Отказ admission до setup отражается в `rejections`,
не добавляя фиктивную операцию. Размер агрегатов фиксирован: без истории,
карт по адресам, raw errors, labels пользователя и новых goroutines/callbacks.

Тесты проверяют конкурентные snapshot-инварианты, порядок восстановления,
таймаут/отмену/TLS/HTTP/протокол, TCP и UDP через H2/H3, заполнение очередей,
лимиты SDK/SOCKS, доставку метрик через SDK events, отсутствие секретов
и чтение нового JSON старым reader, допускающим дополнительные поля.

На Go 1.26.10 прошли полный `go test -race ./...` в корневом модуле и
`integration/external`, `go vet ./...`, сборка CLI, gofmt, проверка границ
protocol-core и Markdown-ссылок. NSS/Neqo в локальные проверки не входят;
их tagged workflows запускаются после публикации коммита.

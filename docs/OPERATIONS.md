# Эксплуатация и платформы — этап 7

[Возможности](FEATURES.md) · [Разработка](DEVELOPMENT.md)

Это продолжение исходного плана: после управления доступом (этап 5) и Linux UDP/TUN (этап 6) проверяется эксплуатация. Нумерация старых файлов CI `stage7`–`stage11` относится к отдельной серии лабораторных работ.

## Что реализовано

- На Unix клиент и сервер обрабатывают SIGINT/SIGTERM: прекращают приём соединений, отменяют активные потоки и освобождают ресурсы. Клиент дожидается завершения своих обработчиков, включая незаконченный SOCKS handshake. На Windows предусмотрен консольный Ctrl+C; интеграции с Windows Service Control Manager пока нет.
- Сервер использует одну атомарно сменяемую пару TLS для TCP/H2 и UDP/H3. На Unix SIGHUP перечитывает сертификат и ключ с исходных путей, проверяет соответствие ключа, PEM и срок действия. Ошибка сохраняет последнюю рабочую пару. Содержимое ключей в журнал не попадает.
- Новые TLS handshake получают новую пару. Уже открытые соединения не обрываются из-за обновления; возобновлённые TLS-сессии могут сохранять прежнюю идентичность. При SPKI pin и смене ключа сначала обновите доверенные pin у клиентов. CA и проверка имени сервера остаются включены.
- CI `Native platform operations` выполняет реальные тесты на Linux, macOS и Windows: TLS-обновление для H2/H3, освобождение обоих слушателей, отмена H2/H3/WSS/XHTTP/bond и незавершённых SOCKS-соединений. Unix дополнительно проверяет SIGHUP и чистый выход по SIGTERM отдельного процесса. Windows проверяет отмену через контекст; доставку Ctrl+C внешнему процессу этот тест не моделирует.

## Обновление сертификата на Unix

1. Подготовьте новую полную цепочку PEM и соответствующий приватный ключ вне публичного web-root. Сохраните права и владельца, позволяющие читать их только нужному сервису.
2. Замените **оба** файла по прежним путям. Отправляйте SIGHUP после завершения обеих замен. Если приходит сигнал между заменами, несовпадающая пара будет отвергнута; после установки обоих файлов сигнал нужно повторить.
3. Выполните `kill -HUP SERVER_PID` для конкретного PID сервера либо настройте `ExecReload=/bin/kill -HUP $MAINPID` в собственной systemd-службе. В управляемом режиме тот же SIGHUP независимо перечитывает политику доступа; политика и сертификат не являются одной транзакцией.
4. Убедитесь в сообщении `TLS certificate reloaded for new handshakes` и проверьте новое проверенное TLS-соединение. При отказе журнал сообщает `TLS certificate reload rejected; previous certificate retained`.

На Windows SIGHUP отсутствует: после замены пары нужен контролируемый перезапуск. Сервер отказывается стартовать с некорректной, просроченной или ещё не действующей парой. Сертификаты не выпускаются автоматически — ACME и расписание обновления остаются у оператора.

## Границы завершения этапа

| Проверка | Состояние в этой части работ |
|---|---|
| Остановка и отмена активных соединений | Реализованы; тесты Go и отдельного Unix-процесса |
| Смена сертификата и отказ неверного обновления | Реализованы для H2/H3; Unix-сигналы и атомарная публикация |
| Исполнение на целевых ОС | Добавлена матрица нативных CI runners; результат смотрите на конкретном коммите |
| Длительные нагрузки и восстановление | Имеется отдельный ограниченный Linux NSS/Neqo soak; длительные целевые прогоны ещё не закрыты |
| Установка, обновление, откат и восстановление | Требуют отдельных системных сценариев и сохранения приватной конфигурации |
| Подписанные выпуски и Apple notarization | Требуют ключей/учётных данных владельца; здесь не заявлены |

Этап 7 целиком остаётся открытым до проверки последних трёх строк. Прохождение loopback-тестов не подтверждает устойчивость в реальных сетях, на всех версиях ОС или безопасность установщика.

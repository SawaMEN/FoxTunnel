# Эксплуатация и платформы — этап 7

[Возможности](FEATURES.md) · [Разработка](DEVELOPMENT.md)

Это продолжение исходного плана: после управления доступом (этап 5) и Linux UDP/TUN (этап 6) проверяется эксплуатация. Нумерация старых файлов CI `stage7`–`stage11` относится к отдельной серии лабораторных работ.

## Что реализовано

- На Unix клиент и сервер обрабатывают SIGINT/SIGTERM: прекращают приём соединений, отменяют активные потоки и освобождают ресурсы. Клиент дожидается завершения своих обработчиков, включая незаконченный SOCKS handshake. На Windows предусмотрен консольный Ctrl+C; интеграции с Windows Service Control Manager пока нет.
- Сервер использует одну атомарно сменяемую пару TLS для TCP/H2 и UDP/H3. На Unix SIGHUP перечитывает сертификат и ключ с исходных путей, проверяет соответствие ключа, PEM и срок действия. Ошибка сохраняет последнюю рабочую пару. Содержимое ключей в журнал не попадает.
- Новые TLS handshake получают новую пару. Уже открытые соединения не обрываются из-за обновления; возобновлённые TLS-сессии могут сохранять прежнюю идентичность. При SPKI pin и смене ключа сначала обновите доверенные pin у клиентов. CA и проверка имени сервера остаются включены.
- CI `Native platform operations` выполняет реальные тесты на Linux, macOS и Windows: TLS-обновление для H2/H3, освобождение обоих слушателей, отмена H2/H3/WSS/XHTTP/bond и незавершённых SOCKS-соединений. Unix дополнительно проверяет SIGHUP и чистый выход по SIGTERM отдельного процесса. Windows проверяет отмену через контекст; доставку Ctrl+C внешнему процессу этот тест не моделирует.

## Обновление сертификата на Unix

1. Подготовьте новую полную цепочку PEM и соответствующий приватный ключ вне публичного web-root. Сохраните права и владельца, позволяющие читать их только нужному сервису.
2. Замените **оба** файла по прежним путям. Отправляйте SIGHUP после завершения обеих замен. Если приходит сигнал между заменами, несовпадающая пара будет отвергнута; после установки обоих файлов сигнал нужно повторить.
3. Выполните `kill -HUP SERVER_PID` для конкретного PID сервера либо настройте `ExecReload=/bin/kill -HUP $MAINPID` в собственной systemd-службе. В управляемом режиме тот же SIGHUP независимо перечитывает политику доступа; политика и сертификат не являются одной транзакцией.
4. Убедитесь в сообщении `TLS certificate reloaded for new handshakes` и проверьте новое проверенное TLS-соединение. При отказе журнал сообщает `TLS certificate reload rejected; previous certificate retained`.

На Windows SIGHUP отсутствует: после замены пары нужен контролируемый перезапуск. Сервер отказывается стартовать с некорректной, просроченной или ещё не действующей парой. Сертификаты не выпускаются автоматически — ACME и расписание обновления остаются у оператора.

## Восстановление H3 после потери QUIC-пути

Тайм-аут установки запроса теперь помечается причиной `context.DeadlineExceeded`. Go H3 выводит соответствующий кэш соединений из использования для **новых** запросов. Уже открытые response body удерживают прежний кэш до явного закрытия: чужой живой поток не прерывается из-за тайм-аута соседнего запроса. Изменение не повторяет отправленный запрос, не меняет TLS-проверку и не включает fallback на другой протокол. Обычная отмена вызывающей стороной и HTTP-отказы сами по себе не запускают смену кэша.

Отдельный тест с UDP-шлюзом блокирует прежний QUIC-путь без `CONNECTION_CLOSE`, пропускает новый путь, проверяет окончание setup по тайм-ауту и новое соединение, затем восстанавливает старый путь и проверяет сохранённый поток. Счётчик реальных выходных TCP-соединений подтверждает отсутствие повторной отправки. Проверка выполняется на трёх ОС. Начальные испытания до исправления давали около 85 секунд восстановления на Windows; актуальное время и соблюдение 30-секундного бюджета проверяются на конкретном коммите CI.

## Установка, обновление и откат CLI

`python scripts/deploy_cli.py --root /private/foxtunnel …` управляет отдельной пользовательской установкой. Linux NSS устанавливается из полного официального `.tar.gz` со всеми библиотеками и лицензиями; автономные Go-сборки Linux/macOS/Windows — через `--binary`. Сырой NSS-бинарник без архива отвергается. Для Windows используйте закрытый пользовательский каталог с подходящими ACL; Unix-каталоги должны принадлежать оператору и иметь права 0700.

Перед исполнением новой сборки установщик делает приватную копию и сверяет SHA-256 с **полученным из доверенного источника** значением. Хеш не является цифровой подписью. Дополнительно проверяются ожидаемые версия, полный commit SHA, целевая ОС/архитектура, wire draft и признак чистой сборки. Для NSS повторно используется проверка формата существующих release-архивов: пути, типы файлов, размеры, происхождение библиотек и их хеши.

Пример для Linux (значения `EXPECTED_*` и путь архива задаёт оператор по проверенному выпуску):

~~~bash
python3 scripts/deploy_cli.py --root "$FOXTUNNEL_INSTALL_ROOT" install \
  --archive "$REVIEWED_ARCHIVE" --sha256 "$EXPECTED_SHA256" \
  --version "$EXPECTED_VERSION" --commit "$EXPECTED_COMMIT"
python3 scripts/deploy_cli.py --root "$FOXTUNNEL_INSTALL_ROOT" status
python3 scripts/deploy_cli.py --root "$FOXTUNNEL_INSTALL_ROOT" run -- version --json
~~~

Для автономной Go-сборки замените `--archive` на `--binary`. Выполняется только проверенный кандидат с командой `version --json` до активации. Это проверка метаданных и загрузки runtime, а не доступности вашего сервера. После активации перезапустите управляемый вами процесс и проверьте новое соединение. Уже запущенный процесс продолжает работать на прежней версии.

Состояние переключается одним `os.replace` после записи и fsync. На локальной файловой системе читатель видит целиком прежний либо новый JSON. Сборки хранятся отдельно по SHA-256, предыдущая версия сохраняется. Изменение или отсутствие установленного файла блокирует запуск/откат. Конфигурация в `config/` не мигрируется и не перезаписывается; её резервные копии и совместимость со старой версией проверяет оператор. Сетевые настройки и службы ОС установщик не меняет.

~~~bash
python3 scripts/deploy_cli.py --root "$FOXTUNNEL_INSTALL_ROOT" rollback
python3 scripts/deploy_cli.py --root "$FOXTUNNEL_INSTALL_ROOT" run -- version --json
~~~

После повреждения `state.json` можно явно выбрать известную проверенную установку, сохранив конфигурацию:

~~~bash
python3 scripts/deploy_cli.py --root "$FOXTUNNEL_INSTALL_ROOT" recover \
  --release "$KNOWN_INSTALLED_SHA256"
~~~

Блокировка ОС исключает одновременное переключение; после смерти процесса она освобождается ядром. Неполная подготовленная директория или сборка, успевшая сохраниться до сбоя активации, не меняет прежнюю активную версию. Сетевые файловые системы, внезапное физическое повреждение диска и защита от владельца каталога вне этих гарантий. Не удаляйте прежние сборки, пока ими пользуется работающий процесс.

CI выполняет установку двух **лабораторных версий одного исходного кода**, обновление, отказ неверного SHA, откат, восстановление состояния и проверку неизменности конфигурации на Linux/macOS/Windows. Это не проверка совместимости любых исторических версий. Linux amd64/arm64 дополнительно устанавливает и запускает настоящие NSS-архивы из текущего release pipeline. Менеджеры пакетов, Windows Service Control Manager, `.app`/`.dmg` и автоматическая миграция конфигурации сюда не входят.

## Подтверждение происхождения Linux-релизов

В `Versioned binaries` подготовлено подписание SLSA provenance точных байтов обоих Linux NSS-архивов через GitHub OIDC/Sigstore. Используется закреплённая по commit версия `actions/attest`. Разрешения `id-token: write` и `attestations: write` есть только у publish job, которая выполняется при push с проверенным запросом выпуска или release tag. PR и обычный push в main не подписывают и не публикуют выпуск.

Перед подписью загруженные CI-архивы повторно проверяются по release-контракту, версии и исходному commit. Перед `gh release create` проверяются подпись, репозиторий, конкретный workflow, source commit/ref и отсутствие self-hosted runner. Отказ любой проверки блокирует публикацию. Attestation хранится отдельно в GitHub; формат выпуска остаётся прежним — два Linux NSS-архива.

Для **будущего выпуска из этого workflow**, до распаковки и исполнения архива:

~~~bash
gh attestation verify "$REVIEWED_ARCHIVE" --repo SawaMEN/FoxTunnel \
  --signer-workflow SawaMEN/FoxTunnel/.github/workflows/release.yml \
  --source-digest "$EXPECTED_COMMIT" --source-ref "$EXPECTED_SOURCE_REF" \
  --deny-self-hosted-runners
~~~

`EXPECTED_COMMIT` и `EXPECTED_SOURCE_REF` задаются по независимо проверенному запросу выпуска: ref будет `refs/heads/main` для выпуска по запросу либо `refs/tags/v…` для tag-triggered выпуска. Затем применяются обычные проверки архива и установщика. SHA-256 для установки можно вычислить по байтам, чью attestation только что успешно проверили. Инсталлятор сам `gh` не вызывает и без этой проверки по-прежнему полагается на доверенный SHA-256.

Это подпись происхождения архива из workflow, а не Apple Developer ID, Authenticode, независимый аудит или защита от компрометации самого доверенного workflow. Старые выпуски автоматически подписанными не становятся. Настоящая выдача и проверка attestation требуют следующего явно запрошенного выпуска; PR проверяет сборку и контракт, но не выдаёт release-подпись. Apple signing/notarization остаются открытыми.

Первичные источники: [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), [параметры `gh attestation verify`](https://cli.github.com/manual/gh_attestation_verify).

## Нагрузочные прогоны

`scripts/operations_soak.py` запускает отдельные реальные CLI-процессы сервера и клиентов Go H2/H3, проверяет параллельную передачу с точным сравнением echo, RSS/working set, лимиты ресурсов, остановку сервера и восстановление **новых** запросов теми же клиентами. Linux дополнительно считает FD, Windows — handles. На macOS измеряется RSS через `ps`. В отчёт не включаются пароли, пути к ключам или сырые журналы.

В PR матрица каждой ОС работает минимум 180 секунд без досрочного выхода по числу запросов. Метка PR `operations-long` включает 1800-секундный прогон каждой ОС. Ручной запуск `Native platform operations` позволяет выбрать 1800 или 3600 секунд; результат сохраняется как `native-operations-<OS>/report.json`. Отчёт фиксирует запрошенную и фактическую длительность, число попыток/успехов, образцы ресурсов и время восстановления. Частота новых потоков ограничена максимумом 24 в секунду суммарно: это непрерывная параллельная передача, а не стресс-тест исчерпания временных TCP-портов при loopback TIME_WAIT на Windows. Параметры паузы и частоты фиксируются в отчёте. Порог успеха — 99%, RSS ≤512 MiB, рост ≤192 MiB, FD/handles ≤1024, бюджет восстановления новых запросов — 30 секунд. На Windows остановка через `terminate` моделирует принудительное завершение процесса; это не тест graceful Ctrl+C.

~~~bash
go run -buildvcs=false ./integration/operations-cert --out /new/private/lab-cert
python3 scripts/operations_soak.py --binary /path/to/foxtunnel \
  --cert /new/private/lab-cert/cert.pem --key /new/private/lab-cert/key.pem \
  --seconds 3600 --out /private/new-report.json
~~~

Используются только loopback и Go transport. Отдельный Linux NSS/Neqo soak остаётся другим испытанием. Трёхминутный CI smoke не закрывает длительный пункт этапа; нужны сохранённые длительные прогоны целевых систем. Это также не полевое WAN-измерение, проверка TUN, миграции сети или доказательство отсутствия утечек памяти.

### Сохранённый 30-минутный результат

[CI run 39426721584](https://github.com/SawaMEN/FoxTunnel/actions/runs/39426721584) для PR head `a3621705d7b1375df3457c7ce87483652e3c695e` прошёл на трёх ОС. Checkout использовал synthetic merge `5f7aec23cdd1e49c10a800dff4029a318af924f3`; его полный source tree совпадает с tree PR head. Метаданные сборок, источники и точные агрегаты журналов сохранены в [native-operations.json](measurements/2026-10-20/native-operations.json).

| Нативный runner | Фактическая нагрузка, с | H2 успешно / всего | H3 успешно / всего | Восстановление, с |
|---|---:|---:|---:|---:|
| Linux amd64, Ubuntu 24.04 | 1800.140 | 17757 / 17757 | 17757 / 17757 | 1.318 |
| macOS arm64, macOS 15 | 1800.334 | 14346 / 14346 | 14346 / 14346 | 1.418 |
| Windows amd64 | 1800.188 | 20144 / 20145 | 20143 / 20145 | 10.343 |

На Windows за нагрузочный период три запроса из 40290 не завершились успешно; каждый carrier превысил порог 99% (H3 — около 99.990%). Пиковый RSS/working set среди всех процессов трёх ОС — 25.82 MiB, максимальный рост к концу нагрузки — 7.83 MiB. Linux FD ≤11, Windows handles ≤280. Обе остановленные связи обнаружены, новые запросы восстановлены теми же клиентами на всех ОС. Исправление H3 сократило измеренное Windows-восстановление с 84.97 до 10.343 секунды; это конкретное loopback-измерение, а не универсальная гарантия failover.

После этого прогона добавлена отдельная строгая проверка фактического времени восстановления: даже успешный запрос после конца бюджета не закрывает проверку. Четыре детерминированных теста покрывают поздний успех, отказ запуска новой попытки после deadline и повторные попытки только ещё не восстановившихся carriers. На исходном завершающем коммите этапа 7 `28ed89c7ee25c12dd39136f48ee726b45d7764a8` производственный Go-код совпадал с кодом длительного прогона. При последующей интеграции с `main` были сохранены дополнительные изменения безопасности и передачи данных из ветки `up`; старый 30-минутный результат относится к указанному историческому source commit. Для объединённой версии повторяются Go race-тесты, нативные 180-секундные эксплуатационные проверки и SDK-матрица; это отдельные результаты CI.

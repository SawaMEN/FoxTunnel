# Этап 1/8 — FoxTunnel против Xray/VLESS: воспроизводимый baseline

**Статус:** код измерений и проверяющий gate готовы к независимым полевым испытаниям. CI и локальная петля не доказывают производительность на VDS. Полностью закрывать этап можно только после оценки реальных отчётов.

## Что сравниваем

Две запущенные конфигурации с локальными SOCKS5 inbound:
- FoxTunnel (зафиксировать версию/commit, H2/H3, Go/NSS/Neqo).
- Xray/VLESS (зафиксировать версию Xray, REALITY/Vision или XHTTP).

Для WAN-запуска параметры --fox-transport и --vless-transport обязательны: конфигурации должны быть явно указаны оператором. CLI не может доказать, что реально запущен именно этот протокол.

Серверы, exit, DNS, процессор, лимиты и маршруты документируйте приватно, без секретов в Git. Управляемый TCP echo-сервер должен быть доступен обоим exit. Для контроля используйте одинаковые условия или явно укажите отличия. Тест на двух контейнерах одной машины не считается независимыми VDS.

Тест идёт через оба SOCKS5-прокси и проверяет каждый переданный echo-байт. Для коротких запросов измеряется p95 **полного выполнения CONNECT + передачи echo**; для больших — медианная полезная скорость TCP echo (не скорость линии), а также CONNECT p95. Опционально измеряются CPU% и RSS отдельных Linux-процессов. Для UDP используется отдельный измеритель. TCP-проба не измеряет ICMP ping, браузерный отпечаток, обход фильтрации или отсутствие утечек.

## Подготовка

1. Запустите FoxTunnel и Xray/VLESS отдельными процессами на разных локальных SOCKS-портах, например 1080 и 1081. Не передавайте учётные данные в CLI измерителя.
2. В изолированном стенде используйте команду из блока ниже для echo. На внешнем VDS разрешайте слушатель только на приватном интерфейсе и ограничьте доступ firewall по IP. Echo-сервер не аутентифицирован — никогда не открывайте его всему интернету.
3. Зафиксируйте PID именно клиентских процессов Linux; примерные значения ниже замените настоящими. У монитора должен быть доступ к /proc/PID/stat и /proc/PID/status.
4. Создайте приватную директорию reports (chmod 700) вне Git. Выходные файлы создаются эксклюзивно с режимом 0600. Не публикуйте сырые отчёты compare_transports.py: в них содержатся адреса и тексты ошибок.

~~~bash
python3 scripts/echo_server.py --host 127.0.0.1 --port 9000
~~~

## Сбор одного парного измерения

При подтверждённом WAN/VDS маршруте:

~~~bash
python3 scripts/stage1_vless.py \
  --fox-socks 127.0.0.1:1080 --vless-socks 127.0.0.1:1081 \
  --target echo.private.example:9000 \
  --scenario small --fox-transport h2-connect \
  --vless-transport reality-vision --environment wan --confirm-independent-vds \
  --rounds 30 --parallel 4 --warmup 2 \
  --fox-pid 1234 --vless-pid 5678 \
  --out reports/day1-small.json
~~~

Повторите со --scenario bulk и отдельным файлом reports/day1-bulk.json. Размер по умолчанию: **1 KiB** для small, **32 MiB** для bulk. Параметр --bytes меняет размер, но gate не разрешает смешивать его в одном сравнении.

Сделайте измерения минимум в **три разных UTC-дня** с одинаковыми параметрами и независимыми VDS. Локальные эксперименты помечайте --environment lab без флага подтверждения: в production gate они никогда не пройдут.

Ресурсы измеряются как CPU-время и пиковая RSS **целого процесса** за период бенчмарка. Измерения включают возможную фоновую работу; методику нужно скорректировать, если процессы делят железо или выполняют другие задачи. Скрипт не проверяет идентичность указанных PID.

## Проверка результатов

Для small и bulk запускайте gate **отдельно**:

~~~bash
python3 scripts/stage1_vless_gate.py \
  --report reports/day1-small.json \
  --report reports/day2-small.json \
  --report reports/day3-small.json \
  --out reports/small-verdict.json

python3 scripts/stage1_vless_gate.py \
  --report reports/day1-bulk.json \
  --report reports/day2-bulk.json \
  --report reports/day3-bulk.json \
  --out reports/bulk-verdict.json
~~~

**Порог для каждого парного дня:**
- не менее 5 проверенных измерений на конфигурацию; успешность FoxTunnel и VLESS ≥99%; ноль обнаруженных ошибок целостности;
- для **small**: p95 полной задержки (SOCKS CONNECT + echo) FoxTunnel ≤110% VLESS; скорость 1 KiB пакетов не используется как критерий;
- для **bulk**: медианная полезная скорость FoxTunnel ≥90% VLESS, а p95 SOCKS CONNECT ≤110% VLESS;
- для **bulk**: CPU% и пиковая RSS FoxTunnel ≤120% VLESS (оба PID обязательны для прохождения); для small ресурсы информативны;
- минимум 3 разных UTC-дня, один размер нагрузки и одинаковая конфигурация; WAN подтверждён оператором.

Доли вычисляются заново из индивидуальных измерений, а не принимаются из Summary. Выход gate не содержит endpoint/PID/raw ошибок. Даже passed=true означает только условный TCP baseline gate, но не доказательство независимости сети, правильности режима VLESS, устойчивости к ТСПУ, UDP или безопасности.

Запуск офлайн-проверок:

~~~bash
python3 -m unittest discover -s scripts -p 'test_stage1_vless.py' -v
python3 -m py_compile scripts/stage1_vless.py scripts/stage1_vless_gate.py
~~~

## Границы этапа

Текущие [сценарии UDP, loss, jitter и WAN-сравнения Bonding](ADAPTIVE-BONDING-STAGE4.md) полезны дополнительно, но они не заменяют парное сравнение с Xray/VLESS. После получения внешних TCP small/bulk отчётов можно разбирать Fast Path и переходить к следующим этапам.

Версия схемы отчётов Stage 1 после уточнения методики — **2**. Ранние отчёты schema=1 использовать с новым gate нельзя: его необходимо запускать заново, чтобы получить измеренное completion_ms. Для Linux защита от повторного использования PID сверяет /proc/<pid>/stat starttime.


## Дополнение к этапу 1: UDP против Xray/VLESS

UDP сравнение запускается **отдельно**, не через обычный TCP измеритель.
Используется SOCKS5 UDP ASSOCIATE, одна длительная ассоциация на поток,
один общий контролируемый UDP echo адрес для обеих конфигураций.
В отличие от отдельных HTTP-запросов, RTT означает время ответа UDP echo через
полную цепочку SOCKS5 → proxy → VDS → echo → proxy → SOCKS5.

Для работы нужна поддержка SOCKS5 UDP ASSOCIATE в **обоих** локальных
клиентах. У FoxTunnel включайте экспериментальный UDP/UDP Stream,
а у Xray — UDP поддержку inbound/outbound в той конфигурации, которую проверяете.
UDP не будет автоматически работать только потому, что TCP прокси работает.

Контролируемый UDP echo target на изолированной машине:
~~~bash
python3 scripts/udp_echo_server.py --host 127.0.0.1 --port 9001
~~~
На удалённом VDS слушатель должен быть доступен только доверенным exit
через cloud firewall: сервис не имеет авторизации. При явно разрешённом
не-loopback bind потребуется --allow-public на **этом сервере**, только
с изоляцией и ограниченными source IP.

Пример **одного дня** на клиенте (замените адреса своими приватными):
~~~bash
python3 scripts/stage1_udp_vless.py \
  --fox-socks 127.0.0.1:1080 \
  --vless-socks 127.0.0.1:1081 \
  --target echo.private.example:9001 \
  --fox-transport h2-connect \
  --vless-transport reality-vision \
  --environment wan --confirm-independent-vds \
  --rounds 40 --parallel 2 --warmup 3 --timeout 2 \
  --out reports/day1-udp.json
~~~

Повторите с одинаковыми конфигурациями на **трёх разных UTC-днях**,
после чего проверьте:
~~~bash
python3 scripts/stage1_udp_vless_gate.py \
  --report reports/day1-udp.json \
  --report reports/day2-udp.json \
  --report reports/day3-udp.json \
  --out reports/udp-verdict.json
~~~

Условия **условного** UDP gate:
- минимум 20 измерений на конфигурацию за день, > 0 успешных RTT,
  успех ≥99% для FoxTunnel и VLESS и отсутствие ошибок целостности;
- p95 UDP echo RTT FoxTunnel ≤110% VLESS;
- процент неуспешных UDP echo ответов FoxTunnel ≤VLESS + 1 п.п.;
- не менее 3 UTC-дней, одинаковые параметры и один целевой UDP echo.

В отчёте также вычисляется среднее абсолютное изменение RTT между
последовательными успешными ответами **одного потока**. Это описательный
показатель джиттера, а не стандартный interarrival jitter по RFC 3550.
«Потери» в данном тесте — также **не** оценка исключительно потерь пакетов:
сюда входят ошибки SOCKS и истёкшие таймауты.

Схема TCP отчёта = 2, UDP отчёта = 1. Они не объединяются одним gate.
Любой PASS не подтверждает идентичность реальных VDS, качество DPI-маскировки
или работоспособность системного TUN. Публиковать приватные конфигурации,
учётные данные и сырые логи не следует.
